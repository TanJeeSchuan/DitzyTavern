# Production upgrade migration audit

Scope: deployed revision `cc2baa33b2c0c536084bad37b4f5b8f607037d66` to `751586c880145accccba820396c0d2d4b4307fac`, plus working-tree migrations `0024–0026` and `0029`. The first rehearsal found dropped Memory state and absent Box lifecycle rows; the current migration changes address those findings for databases that have not applied these migration indexes yet. Root's production-copy rehearsal reports 2 Chats, 2 nonempty author notes, 678 `memory_collection` rows containing 1,588 claims, 1,866 memory embedding rows, and 496 `generation-memory` activation rows before migration. Both Chats had Memory allowance 20,480; global settings selected extraction Profile 1, embedding Profile 2 and Decision Profile 3. All 3,437 Variants passed the current `readVariantDetails` reader. The copy has zero `source_changed` rows and zero source-hash mismatches among collection records.

## Initial rehearsal findings (superseded by working-tree changes)

- **Memory settings are intentionally discarded.** `0024_amused_dexter_bennett.sql:1-3` drops both settings tables without copying rows. The deployed `memory_settings` held extraction/embedding choices and limits (`cc2…:src/server/database/schema.ts:251-269`); `conversation_memory_settings` held per-Chat allowance, note, label merges, identities and revisions (`cc2…:src/server/database/schema.ts:368-376`). Current readers use `library_data` and `conversation_data` and return defaults when the new keys are absent ([server-settings.ts:13-27](../../src/boxes/memory/server-settings.ts), [server-chat.ts:13-31](../../src/boxes/memory/server-chat.ts)). The project ticket explicitly says “Existing data need not be migrated” and removes the global `enabled` setting ([ticket 20:15-20](../tickets/box-core/20-memory-settings-become-box-data.md)). This is an accepted implementation decision, but production has configured extraction Profile 1, embedding Profile 2 and Decision Profile 3; dropping the row loses those selections and any nondefault global limits. Both Chats' allowance is 20,480, while the new reader fallback is 2,048. Per-Chat notes, identities and merges also reset.
- **All old Memory records are discarded.** `0025_first_solo.sql:1-5` drops `memory_collection` and its catch-up table; there is no `INSERT` into the replacement record store. Production has 678 collection rows containing 1,588 claims: 552 completed automatic records and 126 failed records, with no writer-owned rows. The old table also held source snapshots, traces, status and errors (`cc2…:src/server/database/schema.ts:387-403`). Current Memory reads records from `message_variant_data` under `box:memory`, keyed to the current Box instance ([server-memories.ts:16-32](../../src/boxes/memory/server-memories.ts), [records.ts:14-37](../../src/server/box/records.ts)). **The claim payloads are compatible with the current `memoryRecord` schema:** production checked all 678 as `Value.Check(memoryRecord, { claims: JSON.parse(claims_json) })`. No claim-shape decoder failure blocks preservation. Migration would still need to wrap each payload in a slot (`automatic` or `writer` according to `ownership`), assign a Box insertion `instance`, preserve or derive the `source` value expected by the current slot, and decide how to map failed-record errors. The current reader only folds slots for the Box's current instance ([records.ts:14-37](../../src/server/box/records.ts)); without that lifecycle identity, copied rows would remain unread. Ticket 22 describes the new slot model and intentional reset behavior but not an existing-record migration ([ticket 22:11-24](../tickets/box-core/22-memory-extraction-becomes-a-digest.md)). Thus the SQL definitely discards claims including manual corrections if there were any, while a compatible mapping appears feasible; production currently has no writer-owned records.
- **Memory and Author Note are migrated to absent Box states.** `0017_cheerful_ronan.sql:51-62` renames the `author-note` preset reference and copies nonempty `conversation.author_note` into `conversation_data` as `box:author-note/setup`; `0018_calm_maggott.sql:51,59-60` renames `memory` preset references. Neither migration writes the required `enabled` and `instance` lifecycle keys. Current `readBoxLifecycles` omits a Box with no lifecycle rows, and `readBoxStates` reports that state as `absent` ([setup.ts:28-50](../../src/server/box/setup.ts)); generation captures only participating Boxes. So the author-note text survives as setup but is not active, and a migrated Memory preset slot has no active Memory Box to execute. The Box system requires both lifecycle keys and treats neither as `absent` ([Box system README:333-340](../box-system/README.md)). Root's rehearsal observed this exact absent-state result. This is separate from the documented removal of the old global Memory switch: the migration currently has no explicit per-Chat state mapping.
- **Embedding vectors are dropped, then can be rebuilt.** `0026_freezing_darkstar.sql:1,5-10` drops `memory_embedding_cache` and creates an empty generic `embedding_cache`; it does not copy vectors. The observed 1,866 rows are cache data, not authored claims, and current recall can re-embed text, so this is a performance reset rather than content loss. Ticket 22 had said the cache would stay, so the implementation differs from that ticket decision ([ticket 22:22](../tickets/box-core/22-memory-extraction-becomes-a-digest.md)).
- **Generation Memory activation snapshots are deliberately retired.** `0025_first_solo.sql:3-5` deletes the `generation-memory/activation` variant rows and replaces active/replay activation JSON with `null`; `0026_freezing_darkstar.sql:2-4` removes those columns and deletes every remaining `generation-memory` namespace row. The reported 496 activation rows are therefore not retained. These are derived inspection/recall snapshots, while messages and variants remain; confirm no other durable key used that namespace before treating the broader `0026` delete as safe.
- **Box instruction content rewrite is not a proven loss from this deployed revision.** `0023_many_goliath.sql:51-57` assigns fixed text to `box:phone`, `box:thought`, and `box:mood`, and `''` to other `box:%` blocks. However, at `cc2…` the schema only admitted `memory` and `author-note` referenced rows and required their `content` to be NULL (`cc2…:src/server/database/schema.ts:149-154`); `0017` and `0018` create the `box:` references inside this same upgrade. Thus ordinary data from the stated deployed revision cannot contain customized Box-block content for this SQL to erase. It is only a risk for an already partially upgraded or manually edited database.

## Current dirty-migration review

The original findings about Memory settings, records, lifecycle rows and embedding vectors are **fixed in the working tree** for a database upgrading from the deployed migration index 16. `0024` copies settings and labels, seeds lifecycle rows and the old settings decision selection; `0025` copies compatible claim arrays into instance-keyed record slots; `0026` renames the embedding cache without dropping its rows. Root's rehearsal reads back settings, lifecycle, 678 slots and all 1,866 vectors through current decoders. The claim schema concern is resolved: all 678 legacy claim arrays pass `Value.Check(memoryRecord, { claims: JSON.parse(claims_json) })`.

One edge has no direct slot field: a writer-owned row with `source_changed=true` is displayed stale by the old reader even if its Variant content returns to `source_hash`; new code infers freshness from the hash. The audited production copy has zero such flags and zero source-hash mismatches. Automatic invalidations are stored as failed rows and map to error slots. Pending/running automatic work has no result and is omitted so it can be processed again.

These changed SQL files only run when their journal entries are unapplied. A database where the earlier destructive versions of `0024`, `0025`, or `0026` already ran will skip the revised migration body and cannot restore the deleted values. The copy begins before index 17, so this limitation does not affect the target production upgrade.

## Preserved behavior checked

- Prompt preset rows keep their IDs, order, enabled flag and role across rebuilds in `0017`, `0018`, and `0023`; the only reference changes are the explicit `author-note` → `box:author-note` and `memory` → `box:memory` mappings. The `author_note` value is JSON-quoted into setup before its old column is dropped (`0017:59-60`).
- `0027_spicy_skaar.sql:23-26` copies all generation settings fields, including `request_overrides_json`, during the table rebuild.
- Uncommitted `0029_request_override_namespaces.sql:1-5` uses `json_insert` to add only missing format namespaces, preserving existing provider override objects. Its test exercises both idempotence and preservation of authored nested values ([migrations.test.ts:30-52](../../src/server/database/migrations.test.ts)).
- Every production Variant passed the current `readVariantDetails` decoder (3,437/3,437), so this rehearsal found no persisted Variant-detail incompatibility under the actual data/configuration set.
- No migration in this range changes the `image` or `artifact` tables or references. Images remain in their existing rows; managed artifact files are outside these SQL migrations.

## Reproduction checks

On a disposable copy at `cc2…`, before applying migrations, record counts and sentinel values from `memory_settings`, `conversation_memory_settings`, `memory_collection`, `memory_embedding_cache`, `message_variant_data`, and `conversation.author_note`. Apply migrations through `0029`, then compare:

```sql
SELECT * FROM library_data WHERE namespace = 'box:memory';
SELECT conversation_id, namespace, key, value FROM conversation_data WHERE namespace LIKE 'box:%';
SELECT COUNT(*) FROM memory_collection;
SELECT COUNT(*) FROM message_variant_data WHERE namespace = 'box:memory';
SELECT COUNT(*) FROM embedding_cache;
SELECT name FROM sqlite_schema WHERE name IN ('memory_settings', 'conversation_memory_settings', 'memory_collection');
```

For lifecycle, check that each legacy Chat intended to keep Memory or Author Note has both `enabled` and `instance` rows in its corresponding `box:<id>` namespace, then read `readBoxStates`. To check stale-source behavior, compare `source_changed` and each Variant's current text hash with `source_hash`; the audited copy had zero flagged or mismatched rows. Root's rehearsal confirms the new settings, 678 claim slots, lifecycle rows and 1,866 preserved embedding vectors through current readers.
