# Hide model transport in one deep Model Client module

Model transport will live behind a deep Model Client interface that accepts a provider-neutral Prompt Plan and returns an asynchronous stream of normalized model events. Its implementation directly owns the version-one OpenAI-style REST request translation, credentials, streaming parser, cancellation, errors, and optional usage reporting.

Version one treats the streaming Chat Completions contract as a first-class protocol rather than treating OpenAI's hosted service as a privileged provider. Its connection settings include an exact endpoint URL, credentials, and extra JSON headers. The Model Client posts to that URL exactly as configured; it does not append `/v1/chat/completions` or otherwise infer a provider path. The UI may prefill the conventional OpenAI URL for convenience. Generation settings include a model identifier, ordinary sampling and token parameters, and an extra JSON body object.

Request Overrides are merged late. Extra body fields may override ordinary generation parameters such as `temperature` and `top_p`, and may contain unknown provider-specific fields. They may not override the structural `messages`, `model`, `stream`, `n`, `max_tokens`, or `max_completion_tokens` fields. The Conversation's editable response budget is the single source used by both Prompt Compiler reservation and Model Client output-token translation. The Model Client forces `n: 1` so one Generation always produces exactly one Variant. It also rejects tool-calling fields, audio, and non-text modalities that version one cannot represent. Textual response formatting, including JSON mode, remains allowed. Extra headers may replace `Authorization` to support alternate authentication and routing schemes, but the Model Client rejects transport-owned headers such as `Host`, `Content-Length`, and `Transfer-Encoding`.

Connection Settings choose how the response budget is represented with an `outputTokenParameter` of `max_tokens` by default, `max_completion_tokens`, or `omit`. This changes only the emitted key. `omit` retains local prompt budgeting while leaving the remote output limit unspecified. Request Overrides cannot supply either key independently.

The Model Client may fetch model IDs only from an explicitly configured exact Models endpoint URL using the common `GET` response shape `data[].id`. It reuses the configured credentials and headers, normalizes failures for display, and does not make successful discovery a precondition for generation. Model IDs remain arbitrary user-entered strings.

The version-one translation uses only the broadly compatible `system`, `user`, and `assistant` message roles. It emits one initial `system` message containing System Instruction, both active Participants' Identities, and Scenario in the Prompt Plan's named-block order; then Example Dialogue; then selected Conversation history with roles derived from current Control; and finally a `system` message containing Post-History Instruction. Historical speaker names are already embedded textually by the Prompt Compiler, so the transport does not depend on the optional API `name` field. It intentionally does not emit the newer `developer` role.

The Model Client never automatically retries a failed request. One outbound request is exactly one Generation attempt. A failure before any visible Content or Reasoning Content removes the empty provisional Variant and restores the prior selection; a failure after either kind of output persists the Variant as interrupted. Starting another Variant is the user's explicit retry action, preventing hidden duplicate requests and charges after ambiguous transport failures.

Each request has a configurable stream-inactivity timeout, defaulting to 120 seconds and allowing the user to increase or disable it. There is no total-duration timeout while the stream remains active. Any syntactically valid SSE activity resets the timer, including visible text deltas, reasoning or thinking deltas, usage events, and keepalive comments. Arbitrary partial transport bytes do not. A timeout cancels only that Generation and follows the ordinary interruption rule: a Variant containing visible Content or Reasoning Content persists as interrupted, while a slot containing neither is removed.

When an endpoint streams textual reasoning separately from visible answer content, the Model Client normalizes it as Reasoning Content. The server synchronizes and persists it separately within the Variant, and the client presents it as collapsible output. Reasoning Content counts as reply output for Variant durability even if no visible Content arrives. Version one does not include it in later prompt messages. That is a deliberate deferral rather than a permanent exclusion: future tool-call support may need to return reasoning according to the endpoint's concrete multi-turn contract.

The Model Client normalizes a provider `finish_reason` of `length` as a `length-limited` terminal outcome while retaining the raw finish reason in compact metadata. The Conversation persists that Variant and remains immediately usable; version one does not automatically request or append a continuation.

Version one will not build a provider registry, capability matrix, inheritance hierarchy, or public provider-adapter interface. A provider seam will be extracted inside this module when a concrete second provider creates a real need for multiple Adapters.
