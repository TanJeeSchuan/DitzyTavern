# Lorebooks with keyword and sentence-based semantic matching

## Problem Statement

Writers need recurring facts about their worlds, places and characters to reach the model when they matter to the current scene. DitzyTavern currently has no Lorebook library, attachment model, activation engine or embedding support. Writers must repeat facts manually or leave them permanently in prompt instructions, consuming context even when unrelated to the scene.

Literal keywords alone miss descriptions expressed in different words. Automatically embedding entire lore entries makes activation depend on incidental content rather than the author's intended triggers. Writers also need to understand why a fact appeared or was omitted, inspect the exact writing context before sending it, and investigate an older Variant after the source books have changed.

## Solution

Add shared native Lorebooks with separately authored Keywords and Semantic Triggers. Attach books to Chats or Character/Participant uses, with eligibility scope owned by each attachment. Match against recent selected writing, compare Semantic Triggers with individual sentences, and let each entry combine lexical and semantic results with AND or OR. Support unconditional Always entries and secondary lexical requirements or exclusions.

Insert admitted content through a single movable Lore block in the active Prompt Preset, within an explicit Lore Allowance. Keep writing available through a defined keyword-only fallback when required embeddings are unavailable. The inspected Prompt Plan is exactly the writing context sent to the API; preserve permanent activation evidence per Variant, including the actual Lore text when manually edited.

Provide a popup editor, match tester, standalone SillyTavern lorebook import and native book import/export. Support the agreed subset with clear import warnings rather than promising complete SillyTavern behavior.

2. As a writer, I want to search books and edit ordered entries, so that I can maintain a large world without losing track of its facts.

12. As a writer, I want Cast scope, so that unseated Cast members can supply relevant lore while appearing in the story.

18. As a lore author, I want literal Keywords with case and whole-word controls, so that names and phrases activate deliberately.

20. As a lore author, I want Semantic Triggers separate from Keywords and lore content, so that I can describe relevance independently of the facts to inject.
21. As a lore author, I want sentence-based semantic matching, so that a relevant sentence can match inside an otherwise unrelated long Message.

## Implementation Decisions

1. **Use the existing server-owned architecture.** Add a native Lorebook domain responsible for authored books, entries, import/export, attachment eligibility and activation evidence. Integrate it through the existing Generation preparation and Generation Plan Compiler path used by Send, Sibling Generation, continuation and inspection. Keep embedding I/O outside the pure compiler; pass captured results into deterministic assembly and budget decisions. Do not introduce parallel implementations of lore behavior in the client and server.
2. **Separate shared content from uses.** Persist stable Lorebook and Lore Entry identities, authored metadata, entry order and the chosen matching controls. Attachment records associate a book with a Character, Participant or Chat and own their scope. Chat configuration owns scan depth and Lore Allowance. A separate application-wide configuration owns embedding endpoint, credential, model, threshold and deadline. Derived embeddings are not authored lore.
3. **Keep attachments independent.** Controlled Participant eligibility requires its attached Participant to occupy either control seat for the attempt; Cast eligibility includes any Participant in that Chat's Cast; Chat attachment is independent of Participants. Copy Character attachment lists into Participants when they are created. Book edits stay shared, while later Character attachment edits do not change existing Participant lists. Evaluate eligibility before deduplicating by book identity; one eligible use is sufficient. Explicit duplicates remain independent even when their content is identical.
4. **Use the attempt's Lore Scan Window.** The Chat-owned default is four individual Messages shared by both matchers. Include both authors, the pending human Message on Send and the Selected narrative path applicable to the attempt. Sibling Generation excludes its target and all later Messages. Exclude definitions, preset instructions and Reasoning Content. Scan-depth choice does not determine how much history the model receives.
5. **Keep lexical matching explicit.** Default to case-insensitive whole-word literal Keywords, with case-sensitive and substring options. Support explicitly slash-delimited regexes with flags. Each expression matches inside one complete Message, while primary and secondary results combine across the whole window. Never synthesize a phrase across Message boundaries. Invalid configuration must be reported rather than silently reinterpreted.
6. **Match authored Semantic Triggers against sentences.** Split each scanned Message into sentences without crossing Message boundaries or treating every period as a sentence end. Compare each trigger with each sentence and use its strongest cosine score. Any trigger meeting the entry's effective threshold satisfies its semantic side. The target is the separately authored trigger, never the full entry content or title. Sentence matching does not promise to resolve meaning spread across multiple sentences.
7. **Define one activation rule.** Evaluate only populated primary lists; any Keyword match satisfies the lexical side and any qualifying Semantic Trigger satisfies the semantic side. When both are populated, use the entry's AND or OR, default OR. Neither populated means no conditional match. Always bypasses trigger conditions, including secondary conditions, but not enablement, scope or budget.
8. **Apply secondary conditions after the primary result.** Conditional entries may require any or all secondary Keywords, or exclude when any or all match. These conditions gate semantic hits too. An empty secondary list supplies no additional condition. During keyword fallback these conditions remain active. Disabled entries contribute nothing.
9. **Configure embeddings independently of generation models.** Use one application-wide OpenAI-compatible endpoint and model with write-only credential handling consistent with existing connection secrets. The default cosine threshold starts at editable 0.70 and may be overridden per entry. It is explicitly uncalibrated across models. Provide the match tester rather than claiming a measured relevance guarantee or filling a minimum result quota.
10. **Treat embeddings as reusable derived data.** Tie cached results to exact source text and embedding endpoint/model identity. Reuse compatible vectors, regenerate what is needed after source or configuration changes, and never compare vectors from incompatible configurations. Authoring saves do not depend on embedding completion. Keep credentials out of prompts, records and exports.
11. **Use the approved whole-Generation fallback.** Required embedding work has a configurable deadline initially five seconds. Either obtain a complete semantic evaluation or use keyword-only fallback for the Generation. Failed, missing or unusable required results cannot masquerade as semantic non-matches. Do not mix partial successes with per-entry fallback or use stale vectors. Compatible cached results need no availability probe. In fallback, Keywords alone can satisfy AND entries; semantic-only entries are skipped; secondary conditions and Always behavior remain; inspection and evidence report fallback.
12. **Add exactly one optional Lore slot to recipes.** A Prompt Preset may contain at most one Lore block, including disabled occurrences. Validate this through creation, editing, duplication and native import. The block is a movable referenced slot with editable role defaulting to system. Its content contains admitted literal entry content, without automatic title, score or diagnostic injection. Do not evaluate Prompt Macros in any lore field, even if imported text resembles supported macros.
13. **Match once, then budget.** Capture eligibility and matching results once against the scan window. Budgeting may remove a triggering history Message without changing its entry's eligibility. Do not rerun matching as history is trimmed. Preserve existing safety-allowance and context-limit rules; reserve response budget, fixed preset content and the protected history before lore. If required protected inputs do not fit, preserve the existing explicit failure.
14. **Use the agreed allowance and order.** Initial Lore Allowance is 2,048 estimated tokens per Chat, bounded further by available context. Consider Always before conditional entries; within each group use higher numeric priority, then stable book creation/import order, then editable entry order. Default priority is zero. Admission order is also prompt order. Admit whole entries, skipping oversized entries and continuing. Account for assembly separators and overhead in estimates. Older history uses remaining space. Always is not a budget exemption.
15. **Make preset integration explicit.** Fresh Default recipes contain Lore immediately before history. Existing saved recipes acquire it only through Add Lore Block; do not silently modify even an edited Default. When books are attached but the selected recipe lacks an enabled Lore block, explain inactivity and offer add or enable as appropriate. With no enabled Lore block, skip lore matching and embedding work. Blank custom recipes remain user-authored.
16. **Preserve the inspected input.** The accepted inspected Prompt Plan, including manual edits, is the writing context sent to the API. Do not rematch lore, rerun macros, recover semantic results after fallback, add unseen instructions or silently trim it before sending. Provider translation encodes the plan's content, roles and Generation intent rather than changing them. Invalid, stale or oversized plans may be rejected, never silently repaired and sent.
17. **Capture and invalidate coherently.** Changes to captured book content, attachments, settings or relevant history invalidate a preview. Endpoint recovery alone does not. Explicit Refresh assembles again. Fresh attempts use current saved inputs with the existing attempt-specific control and selected-history rules. Active Generations retain their captured context. Resolve asynchronous embedding work without holding database transactions open or allowing mutable inputs to drift into one accepted attempt.
18. **Retain permanent Variant-owned evidence.** Use the existing durable Variant-data lifecycle for server-owned Lore Activation Records, separate from transient generation replay. Capture the relevant book/entry identities and source values, eligibility, matched text, scores, effective conditions, priority, budget omissions and fallback status needed to explain the attempt. Each retained sibling and interrupted Variant owns its record. Editing source books, source Messages or selections does not rewrite it; source book deletion does not erase it. Deleting the owning Variant deletes its record. Attempts without retained output leave no lasting Variant-owned record.
19. **Separate automatic evidence from manual text.** If inspection edits the Lore block, retain the original automatic explanation plus the final edited Lore text and a manual-edit marker. Do not invent per-entry attribution for arbitrary replacement text. Permanent lore evidence does not require permanently storing the entire Prompt Plan or provider JSON. Expose evidence through existing Variant details and protect its namespace from generic writable data commands.
20. **Expose complete native operations through existing conventions.** Provide typed server commands and reads for book/entry editing, ordering, enablement, attachments and scopes, embedding settings, match testing, native interchange and permanent record inspection. Reuse revision-checked atomic updates and existing HTTP outcome handling. Keep public boundaries centered on user actions rather than exposing database or matcher internals. Continue existing server authority and secret handling.
21. **Follow the accepted popup workflow.** Use a popup editor like Prompt Presets, with search, create, duplicate, import/export and entry editing. Entry text and matching controls have an explicit Save boundary; ordering and enable/disable toggles persist immediately. Book name and description have a separate Save. Dirty close or switch offers Save, Discard and Keep editing. New entries are enabled, conditional, empty-triggered, OR and priority zero. Attachment scope is edited where the book is used. Follow the established responsive and accessible popup/inspection patterns and prefer existing Radix/Shadcn components.
22. **Import a deliberate subset.** Support standalone SillyTavern lorebook JSON plus native book JSON import/export. Map supported authored metadata, entry content, keys, enablement, Always, secondary logic, lexical options and ordering into the native model. Warn about unsupported behavior while keeping supported portions usable. Preserve explicit source-disabled status. Never invent Semantic Triggers from keys/content, promote an unmatchable entry to Always, or evaluate imported macros. Unsupported full-content semantic-only entries may remain enabled but unmatched until edited. Report unsupported recursion, timing, probability, groups, placement and macros explicitly.
23. **Keep interchange independent.** Native exports contain authored book and entry data but exclude attachments/scopes, embedding vectors, credentials and historical evidence. Native reimport and duplication create independent identities. Extraction from PNG Character Cards and SillyTavern export are outside this version. Do not create compatibility layers for unsupported source behavior.
24. **Collapse World Info positions predictably.** New SillyTavern preset import maps the first enabled World Info placeholder in the selected source order to Lore; if all are disabled, retain the first disabled. Omit other World Info positions with warnings about the collapse. Keep the existing selected-order-list import rule. Existing discarded positions cannot be recovered. Native presets with multiple Lore blocks are invalid, including disabled duplicates.
25. **Delete through ownership rules.** Show affected attachments before confirmed shared-book deletion removes the book and those attachments. Detachment alone preserves the book. Keep historical evidence self-contained so that deletion of mutable sources cannot cascade into retained Variant records. Database changes follow the established SQLite and Drizzle workflow. If seed data is added, its equivalent teardown must share the seed data and remove only those rows with dependents first.

## Testing Decisions

1. Test externally observable behavior and meaningful failures. Assert captured provider input, public outcomes, saved state and retained evidence. Do not assert internal file layout, helper call sequences, duplicate declarations or implementation-shaped expectations. Avoid tautological and architectural regression tests.
2. Prefer the existing server Generation/inspection contract boundary as the main feature test seam, using initialized database fixtures and controlled embedding/model responses. Cover Send, Sibling Generation, continuation, preview, acceptance and Variant details through the same production planning path. Introduce an embedding boundary only to control external responses and deadlines, not a separate test-only activation system.
3. Reuse prior art from Prompt Plan inspection tests that capture outgoing provider requests, Prompt Preset generation-capture tests that edit shared recipes during an active attempt, and native preset interchange tests that round-trip authored data through library routes. These patterns already prove the highest useful behaviors for lore.
4. Add focused tests through the existing Generation Plan Compiler and budget interface for exact admission choices, protected context, whole-entry omission, stable ordering, separator estimates and no rematching after history trimming. Use small deterministic fixtures that would fail under a different observable policy.
5. Exercise lexical/semantic decisions through public lore evaluation or the match-test action and representative Generation contracts. Include whole-word versus substring, explicit regex, no cross-Message phrase construction, secondary conditions across Messages, both operators, empty lists, Always, disabled entries and sentence segmentation. Use controlled vectors to verify threshold behavior; do not claim deterministic fixtures prove a real model's retrieval quality.
6. Verify eligibility and durability with the existing Character-to-Participant, Conversation and library contract patterns: copied attachment lists, shared content edits, each scope, overlapping references, independent duplicate identities and deletion impact. Include one ineligible attachment alongside an eligible direct Chat attachment.
7. Verify complete semantic evaluation versus whole-Generation fallback for unavailable, timed-out, missing or invalid required embeddings. Assert the AND override, semantic-only omission, preserved secondary exclusions and visible fallback evidence. Prove compatible cache reuse and source/model change invalidation through public results and controlled endpoint behavior. Avoid live external models in routine automated tests.
8. Prove exact preview sending by comparing the captured outgoing Lore text to the inspected and edited text. Include endpoint recovery between preview and send, changed captured lore inputs, explicit Refresh, and edits while another Generation streams. Invalid or oversized edits must fail rather than be altered and sent.
9. Reuse Variant persistence, macro-write retention and Generation-recovery test patterns for permanent records. Verify sibling independence, retained interrupted output, restart recovery, cleanup after deletion, persistence beyond the existing replay expiry, source edits/deletion and manual Lore-text evidence. Check that generic data mutation cannot rewrite server-owned records.
10. Test import/export through public library and preset contracts: supported-field round trips, independent reimport, source-disabled preservation, warnings without blanket disablement, semantic-only unsupported input, literal macros, first-enabled World Info placement, all-disabled placement and native duplicate-slot rejection. Invalid input must not partially mutate saved library state.
11. Perform manual browser verification for popup Save/Discard/Keep editing, immediate toggles/order, attachment scope, match explanations, missing-slot guidance and responsive layouts. No UI tests, per repository instruction. Do not write automated tests solely for reversible layout or copy changes.
12. Run the project's required checks and relevant server tests during implementation. The present work publishes a specification; it does not claim the unimplemented feature has passed tests.

## Out of Scope

- Global book activation; books contribute only through the agreed Chat and Character/Participant attachments.
- Recursive activation, probability, inclusion groups, sticky activation, cooldown and delay.
- Model-created or model-updated memory and tool-call memory workflows.
- Embedding full entry content or combining semantic input into whole-scene or overlapping-passage matching.
- Per-entry or per-book scan-depth overrides, per-entry history-depth placement and named outlets.
- Macro evaluation in any lore field, including content and imported expressions.
- Multiple Lore blocks within one Prompt Preset.
- Bundled embedding-model execution or a general embedding-provider/plugin framework.
- Extracting embedded books from PNG Character Cards, SillyTavern export, complete source compatibility and preservation of unsupported execution paths.
- Permanent storage of complete Prompt Plans or raw provider requests merely to support lore explanations.
- Automatic changes to existing saved prompt recipes.
- Automated UI tests and tests that enforce internal architecture rather than behavior.

## Further Notes

The user approved the complete 36-decision design and requested publication as one parent feature work item with the ready-for-agent label. The spec is ready for implementation planning; this publication does not create implementation child tickets or claim implementation completion.

ADR-0039 records shared native Lorebooks and attachment-owned scope; ADR-0040 records authored Semantic Triggers, conditions and fallback; ADR-0041 records one budgeted Lore block; ADR-0042 states that the inspected Prompt Plan reaches the API without reassembly; ADR-0043 makes Lore Activation Records permanent with their Variants. These extend the earlier lorebook deferrals and existing prompt-planning, preset, inspection and Variant ownership decisions.

Two intentional differences from SillyTavern matter: semantic matching targets separately authored triggers rather than entry content, and secondary Keyword conditions constrain semantic hits. The explicitly approved embedding-unavailability fallback is also an intentional exception to the repository's general no-fallback guidance; it does not authorize unrelated compatibility paths.

Source research used SillyTavern release commit 8172dcd0ee672d3cd9a5e5f7af134f91a45cd2b8 and documentation commit 70e5e4d3c239253fca4692fe82e3936cb9c4b1b1. Those sources are behavioral reference material, not the required internal architecture. The initial 0.70 threshold and four-Message scan default are chosen starting settings, not measured claims of semantic quality.
