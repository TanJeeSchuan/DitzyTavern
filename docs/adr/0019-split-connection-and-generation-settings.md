# Split global connection settings from Conversation Generation Settings

Connection Settings own a collection of Connection Profiles, all of whose chat Profiles are available in every Conversation's model selector. Profile display names are required and unique under case-insensitive comparison. Each Conversation stores its selected Profile ID and provider model ID together; there is no global active Profile. A new installation with no Profiles cannot Generate. Creating a chat Profile assigns it to Conversations that do not yet have a selected Profile; an Embeddings Profile is never auto-assigned, because Conversations cannot generate with it. Deleting a Profile leaves affected Conversations unconfigured through a null selection. An app-owned Connection Preset is a factory: selecting one creates a new Profile by copying the Preset's recommended Model Backend, concrete AI SDK Adapter, Pinned Models, and complete ordinary defaults, including API Format and request URL, after which the Profile is independently editable. Bundled Presets do not automatically create empty Profiles, and later Preset changes do not silently mutate Profiles already created from them. Editing the copied URL never silently changes the Adapter. Presets do not invent optional attribution headers such as OpenRouter's `HTTP-Referer` or `X-OpenRouter-Title`; users may add them explicitly as custom headers.

Version one bundles exactly DeepSeek, OpenRouter, Generic OpenAI Compatible, and Embeddings Presets. DeepSeek uses Chat Completions, request URL `https://api.deepseek.com/`, exact Models URL `https://api.deepseek.com/models`, Automatic Model Backend, the DeepSeek AI SDK Adapter, and initially pins `deepseek-v4-flash` and `deepseek-v4-pro`. OpenRouter uses Chat Completions, request URL `https://openrouter.ai/api/v1/`, exact Models URL `https://openrouter.ai/api/v1/models`, Automatic Model Backend, the OpenRouter AI SDK Adapter, and initially pins `deepseek/deepseek-v4-flash`, `google/gemma-4-31b-it`, and `z-ai/glm-5.3` in that order. Generic OpenAI Compatible uses Chat Completions, Automatic Model Backend, the OpenAI Compatible AI SDK Adapter, blank request and Models URLs, and no Pinned Models. Embeddings is a blank profile using the Embeddings API Format, which Memory recall uses instead of chat generation, with a five-second timeout. The Profile owns its API Format, request URL, credential, extra request headers, output-token representation, Model Backend preference, AI SDK Adapter, Pinned Models, and Backend Options.

Connection Profiles reserve OpenAI Chat Completions, OpenAI Responses, and Anthropic Messages as chat API Format vocabulary, but version one makes only Chat Completions selectable for chat. Embeddings is a separate, selectable API Format for Memory indexing and recall. Responses and Messages remain unavailable until their distinct shaping rules are designed. A request URL whose parsed pathname ends in `/` is a base URL: for Chat Completions the application appends `chat/completions`. A URL with a non-empty final path segment is an exact request URL and remains unchanged, including nonstandard paths such as `/generate`. The UI shows the resolved request URL before Apply, and every compatible Model Backend must use that same resolved destination.

Each Conversation owns one provider-neutral response budget. Its selected Connection Profile defaults to automatic API Format translation. Chat Completions Profiles may override the wire representation with `max_tokens`, `max_completion_tokens`, or `omit`. An explicit key changes only the wire representation, while `omit` retains local Prompt Compiler budgeting without sending a remote output limit. Responses and Messages translation remain deferred with the rest of those Formats' shaping.

The dedicated credential remains an opaque write-only Profile value. Preset plus API Format determine its standard authentication meaning, and each compatible Model Backend must apply equivalent standard authentication without exposing header-name or prefix configuration. Endpoints with unusual authentication use write-only custom headers instead and may leave the dedicated credential unset.

Shared connection details belong to the Connection Profile rather than its Model Backend. Switching between compatible Backends reuses the same endpoints, credentials, headers, timeouts, output-token representation, and discovery configuration; only genuinely Backend-specific switches live in Backend Options. `Automatic` uses the Preset's recommended compatible Backend unless the user pins another one. The resolved Backend is fixed before a request starts and never changes as an automatic retry or fallback during that Generation.

Each Conversation owns its Connection Profile and model selection, sampling parameters, context limit, response budget, and extra request body fields so its behavior remains independently tunable and does not change when another Conversation is configured.

Conversation-owned Request Overrides are namespaced by API Format. Only the selected Connection Profile's Format namespace is merged into a request; overrides saved for other Formats remain editable application state but are never transmitted after a Profile switch.

A Connection Profile may also contain an optional exact Models endpoint URL. A user-triggered refresh performs the standard OpenAI-style `GET`, reuses configured credentials and headers, and reads `data[].id`. It trims surrounding whitespace, removes empty and exactly duplicated IDs, preserves the remaining IDs' original casing and characters, and sorts them case-insensitively for display. A successful refresh atomically replaces a persisted per-Profile discovery catalog; a failed refresh leaves that catalog untouched and reports the failure. The catalog survives server restarts but is cache state separate from editable Connection Settings: Refresh neither increments the Connection Settings revision nor invalidates a Profile draft. Applying a different Models URL clears the old catalog because it describes another endpoint, while preserving Pinned Models. Version one does not persist refresh history or stale-state metadata. The server never derives the Models URL from the Chat Completions endpoint; when it is absent Refresh is unavailable, while generation and free-text model entry remain available.

Each Profile owns an ordered Pinned Models list seeded by its Connection Preset. In the Conversation model combobox, opening without a query shows those pinned IDs in the order they were starred. Typing offers non-binding autocomplete across the complete persisted discovery catalog while always allowing an arbitrary free-text value to be committed. Each model row has an independent star toggle: starring appends the ID to Pinned Models, un-starring removes it, and selecting a model never changes its star. Any non-empty arbitrary model ID may be pinned even when discovery did not return it. Autocomplete is ordinary control behavior rather than another saved preference. Discovery is advisory: a custom or previously selected ID remains valid application state even when it is absent from the latest result, and refreshing the catalog never rewrites either Conversation settings or Pinned Models.

Participants and Characters own no model or sampling configuration. Reassigning the model Control seat changes the responding identity and applicable Participant Definition without silently changing the endpoint, model, token limits, sampling parameters, or Request Overrides. The user may edit Conversation Generation Settings before starting the newly active Participant's Generation.

Generation Settings remain editable while sibling Variants are running. Each Generation snapshots its effective settings, selected Connection Profile identity and revision, and resolved Model Backend at start. The resulting Variant records that safe provenance in `message_variant_data` for inspection, because sibling Variants of one Message may use different settings or connection revisions. Connection Secrets, headers, and connection URLs are neither copied into Variants nor exposed through this provenance.
