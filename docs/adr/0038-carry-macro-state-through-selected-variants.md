# Carry Macro State through selected Variants

Macro Variables are scoped to a Conversation and a Prompt Preset, identified by the preset's stable identity. Only selected Variants' writes in that preset's namespace affect the Macro State used by future Generations. Each sibling evaluates from the state before its target Message and has its own resulting state. A background Variant finishing must not overwrite the state contributed by the selected Variant. This keeps persistent values aligned with the user's chosen writing instead of request or completion order.

Switching to a never-used preset starts with empty variables. Switching back derives that preset's state from the current Selected narrative path; it does not restore writes from unselected alternatives. Rename and ordinary preset edits preserve its namespace, while duplication creates a separate one. Each attempt must retain its originating preset identity so a later switch cannot misattribute its writes. This deliberately prevents cross-preset variable sharing, and variables such as `turn` are preset-specific.

For example, if the incoming state has `turn = 5` and the prompt increments it once, every sibling produces `turn = 6`. A following Message generation starts from 6 and can increment to 7. Random values can differ between siblings: if A records `weather = rain` and B records `weather = sun`, selecting B carries sun into subsequent generation. Current preset and definition edits still apply per attempt, and already captured attempts remain fixed under ADR-0037.

Saving an unselected Variant's state does not make it effective for future generation. The state must be available if that Variant is later selected, but it must not change another Variant's captured prompt or variable inputs.

Variable changes follow the existing Variant-retention rules with no special treatment for interruptions or errors. A retained Variant with Content or Reasoning retains its macro writes and contributes them when selected. An attempt removed for producing neither contributes no writes.

Derive Macro State by applying the active preset's recorded writes from selected Variants in Message order. A later assignment to the same variable wins; deletion removes the earlier value. Record the evaluated assignment or deletion, not a macro expression to execute again. Reads do not create writes. This distinguishes a Variant's own writes from the values it inherited and avoids copying obsolete inherited values into the effective state.

Changing an older selection leaves later Messages, text, and recorded writes unchanged. For example, if 1a assigns a variable X, 1b assigns that same variable Y, and selected 2a assigns it Z, selecting either 1a or 1b still leaves Z for the next read. If 2a made no write to that variable, the earlier selected assignment would determine its value. Previously expanded text is never reevaluated or rerolled.

Users can view and edit Macro Variables in a Variables panel that identifies the active preset and inspected history position. It shows effective names and values and their originating Message/Variant, supports add, edit, and delete, and accommodates long text values. Follow DESIGN.MD's secondary inspection-panel placement and narrow-layout layering.

Manual edits attach to the selected Variant at the inspected position. Editing an inherited value records a write there rather than rewriting its earlier source. Those edits affect following Messages only while that Variant is selected; they do not change another sibling's pre-target input. To change input for a sibling generation, edit the state before its target Message. Before the first Message, users can edit initial values scoped to the Conversation and preset. Initial values default to empty.

Use the existing `message_variant_data` storage for preset-keyed Variant write records, including manual writes. It already retains data through selection changes and cascades deletion with the owning Variant. Store preset-scoped initial values in `conversation_data` and apply selected Variant writes after that baseline. The macro module owns record validation and state derivation; generic storage does not define macro behavior. Do not store the effective state as one mutable Conversation-wide value. Deleting a variable records an explicit deletion at the edited position so an older inherited value does not reappear.

This replaces the proposed acceptance-order mutation of one shared variable store. It is an intentional DitzyTavern persistence rule, not a claim of identical SillyTavern behavior. The physical storage and lookup representation remain implementation details; the state derivation must use recorded writes, not reparsing earlier prompts or model output. Memory tool calls and model-produced macro execution are outside this state-update mechanism.
