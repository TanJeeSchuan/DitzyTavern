## Facts

### Entry point and the engine switch

`substituteParams(content, options)` is the single substitution entry point ([`script.js:2921-2955`](D:/Projects/SillyTavern/public/script.js:2921)). It builds a `MacroEnv` with `MacroEnvBuilder.buildFromRawEnv` and calls `MacroEngine.evaluate(content, env)` ([`script.js:2941-2954`](D:/Projects/SillyTavern/public/script.js:2941)). When `power_user.experimental_macro_engine` is off it falls back to the legacy regex engine ([`script.js:2936-2939`](D:/Projects/SillyTavern/public/script.js:2936), [`macros.js:610-715`](D:/Projects/SillyTavern/public/scripts/macros.js:610)). The docs say the engine is enabled by default for new installations and toggleable under User Settings. The engine is synchronous and runs in the browser; multiple built-in handlers read DOM/global state, so it is not a pure function.

### Grammar and syntax as the lexer/parser implement it

**Delimiters.** A macro is exactly `{{` … `}}` ([`MacroLexer.js:53-78`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroLexer.js:53)). The lexer is mode-based (plaintext → macro definition → identifier end → args → filter modifier → variable modes) ([`MacroLexer.js:175-293`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroLexer.js:175)).

**Macro names.** `MACRO_IDENTIFIER_PATTERN = /^[a-zA-Z][\w-_]*$/` — must start with a letter, then word characters, underscores, or hyphens ([`MacroLexer.js:8-17`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroLexer.js:8)). `//` is an allowed special identifier for comments ([`MacroRegistry.js:693-697`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroRegistry.js:693)). Macro lookup is **case-insensitive**: the registry keys definitions by `name.toLowerCase()` ([`MacroRegistry.js:302`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroRegistry.js:302), [`MacroRegistry.js:339-355`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroRegistry.js:339)), and `env.dynamicMacros` keys are lowercased too ([`MacroEngine.js:176-178`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroEngine.js:176)). The docs state `{{User}}`, `{{USER}}` and `{{user}}` are the same macro ([Macros §Basic Syntax](https://docs.sillytavern.app/usage/core-concepts/macros/)).

**Arguments.** The parser accepts three separator styles: `::` for multiple unnamed arguments (`$AT_LEAST_ONE_SEP`), a single optional legacy `:` before one argument, or whitespace directly after the identifier ([`MacroParser.js:136-160`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroParser.js:136), [`MacroLexer.js:74-78`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroLexer.js:74), [`MacroLexer.js:208-212`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroLexer.js:208)). Arguments may contain nested macros, quotes, `=`, `:`, single braces, newlines, and arbitrary non-`}}` text ([`MacroParser.js:162-184`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroParser.js:162), [`MacroLexer.js:150-157`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroLexer.js:150)); whitespace inside the braces is lexed and skipped ([`MacroLexer.js:99`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroLexer.js:99), [`MacroLexer.js:197-198`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroLexer.js:197)). `{{ macroName :: arg1 :: arg2 }}` with spaces is documented as equivalent to the compact form ([Macros §Whitespace](https://docs.sillytavern.app/usage/core-concepts/macros/)). There is no named-argument implementation: `namedArgs` is hard-coded `null` ([`MacroRegistry.js:433`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroRegistry.js:433)).

**Flags.** Flag symbols sit between `{{` and the identifier: `! ? ~ # /` plus `>` ([`MacroLexer.js:55-68`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroLexer.js:55)). Only two are implemented ([`MacroFlags.js:27-77`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroFlags.js:27), [`MacroFlags.js:93-136`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroFlags.js:93)):

| Flag | Meaning | Status |
| --- | --- | --- |
| `/` | closing tag of a scoped macro, `{{/name}}` | implemented |
| `#` | preserve whitespace: disables auto-trim/dedent of scoped content; also accepts legacy `{{#if ...}}` | implemented |
| `!` | immediate resolve | parsed, `implemented: false` |
| `?` | delayed resolve | parsed, `implemented: false` |
| `~` | re-evaluate | parsed, `implemented: false` |
| `>` | filter/pipe mode for `\|` output filters | parsed, `affectsParser: true`, not implemented |

**Scoped macros.** Content between an opening macro and its `{{/name}}` closing tag becomes the macro's **last unnamed argument** ([`MacroCstWalker.js:1131-1255`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:1131)). Pairing is case-insensitive ([`MacroCstWalker.js:236`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:236), [`MacroCstWalker.js:1341`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:1341)) and nested scopes are discovered by re-parsing the parent's scoped content ([`MacroCstWalker.js:1101-1122`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:1101)). A pair is only merged if adding one more argument keeps the macro's declared arity valid; list-argument macros (`list: true`) can **never** take scoped content ([`MacroCstWalker.js:1296-1321`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:1296)). Unmatched `{{/name}}` closing tags stay raw text ([`MacroCstWalker.js:1209-1214`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:1209)). Empty scoped content is passed as an empty last argument ([`MacroCstWalker.js:425-429`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:425)). Unless the `#` flag is set, scoped content is trimmed and dedented: the indentation of the first non-empty line is removed from every line that has at least that much indentation ([`MacroCstWalker.js:440-443`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:440), [`MacroEngine.js:372-413`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroEngine.js:372)).

**Escaping.** The engine has no "escaped macro" token. A macro is only recognized when the two `{` are adjacent, so the documented escape is to separate every brace with a backslash: `\{\{notAMacro\}\}` ([Macros §Escaping](https://docs.sillytavern.app/usage/core-concepts/macros/)). Any `\{` or `\}` left in the evaluated text is unescaped by a post-processor `text.replace(/\\([{}])/g, '$1')` ([`MacroEngine.js:302-308`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroEngine.js:302)). Consequently `\{{user}}` is **not** an escape: the `{{user}}` still parses and resolves (the leading `\` is not adjacent to a `{` after evaluation), whereas DitzyTavern currently renders it literally.

**Malformed input.** An unterminated macro whose identifier parsed (e.g. `{{ hehe`) is flattened back to plain text and logged as a syntax warning; an invalid start such as `{{§§` stays plain text with no macro recognition at all; a dangling `{{` before a later valid macro does not stop the later macro from resolving ([`MacroCstWalker.js:980-1032`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:980), engine tests [`MacroEngine.e2e.js:244-294`](D:/Projects/SillyTavern/tests/frontend/MacroEngine.e2e.js:244)). An empty input returns `''` without parsing ([`MacroEngine.js:117-120`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroEngine.js:117)).

### Variable shorthands and operators

Variable shorthand starts with `.` (local) or `$` (global), entering a dedicated lexer mode before macro flags ([`MacroLexer.js:102-113`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroLexer.js:102), [`MacroLexer.js:188-191`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroLexer.js:188)). Names follow `/[a-zA-Z](?:[\w\-_]*[\w])?/` — must start with a letter and end with a word character, so `my-` is invalid ([`MacroLexer.js:20-26`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroLexer.js:20), [`MacroLexer.js:107-113`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroLexer.js:107)). Variable names are **not** case-normalized, unlike macro names. There is no `@@` prefix.

Operators, with exact runtime semantics ([`MacroCstWalker.js:512-784`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:512)):

| Operator | Operation | Result |
| --- | --- | --- |
| none | get | value, normalized to string |
| `=` | set | `''` |
| `++` | increment via `vars.inc` | new value |
| `--` | decrement via `vars.dec` | new value |
| `+=` | `vars.add` (numeric add, string append, or array push per the variable library) | `''` |
| `-=` | numeric subtract; non-numeric value logs a runtime warning and changes nothing | `''` |
| `\|\|` | fallback if falsy (`''`, `0`, `off`, `false`); fallback lazily evaluated | value |
| `??` | fallback only when the variable does not exist; fallback lazily evaluated | value |
| `\|\|=` | set-if-falsy, returns final value | value |
| `??=` | set-if-undefined, returns final value | value |
| `==` / `!=` | string comparison (`true`/`false`) | `'true'`/`'false'` |
| `>` `>=` `<` `<=` | numeric comparison; non-numeric operands warn and return `'false'` | `'true'`/`'false'` |

Values after `=`/`+=` may contain nested macros, which are resolved only if the operator actually needs the value ([`MacroCstWalker.js:125-133`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:125), [`MacroCstWalker.js:620-631`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:620), [`MacroCstWalker.js:794-854`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:794)). The shorthand ops map to the same `SillyTavern.getContext().variables` API as the named macros ([`MacroCstWalker.js:642-658`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:642), [`st-context.js:256-275`](D:/Projects/SillyTavern/public/scripts/st-context.js:256)).

### Evaluation pipeline

1. **Pre-processors** rewrite legacy syntax before parsing: `{{time_UTC-10}}` → `{{time::UTC-10}}`; `<USER>`/`<BOT>`/`<CHAR>`/`<GROUP>`/`<CHARIFNOTGROUP>` → macro equivalents ([`MacroEngine.js:273-294`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroEngine.js:273)). Priorities: core 0–50 reserved.
2. **Lexer → parser.** `MacroParser.parseDocument` tokenizes with chevrotain, builds a CST with error recovery enabled, and returns lexing/parser errors ([`MacroParser.js:19-29`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroParser.js:19), [`MacroParser.js:195-211`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroParser.js:195)).
3. **CST walker.** Collects top-level plaintext/macro items, sorts by offset, pairs scoped macros, then walks items in order ([`MacroCstWalker.js:93-153`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:93), [`MacroCstWalker.js:305-353`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:305)).
4. **Argument/scope resolution.** For each macro, each argument is evaluated first (nested macros innermost-first) by slicing the argument text, re-parsing it as a standalone document, and walking it recursively ([`MacroCstWalker.js:407-422`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:407), [`MacroCstWalker.js:868-958`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:868)). Macros declaring `delayArgResolution: true` receive raw argument text instead and call `resolve()` themselves; only `{{if}}` does this among built-ins ([`MacroCstWalker.js:396-413`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:396), [`core-macros.js:158`](D:/Projects/SillyTavern/public/scripts/macros/definitions/core-macros.js:158)).
5. **Handler dispatch.** `MacroEngine.#resolveMacro` checks `env.dynamicMacros` first (case-insensitively), then the registry. An unknown macro returns its raw `{{...}}` text, with any nested macros already resolved; no warning is issued ([`MacroEngine.js:167-218`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroEngine.js:167)); this is asserted by the engine tests ([`MacroEngine.e2e.js:89-99`](D:/Projects/SillyTavern/tests/frontend/MacroEngine.e2e.js:89)).
6. **Registry execution.** Arity is validated against `minArgs`/`maxArgs` (and list bounds); a strict failure throws a `MacroRuntimeError`, which `#resolveMacro` catches, logs as a runtime warning, and leaves the macro raw. Non-strict failures warn and continue. Declared positional argument types are validated the same way ([`MacroRegistry.js:396-461`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroRegistry.js:396), [`MacroRegistry.js:736-788`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroRegistry.js:736)).
7. **Normalization and post-process.** Handler results are normalized (null/undefined → `''`, Date → ISO string, object → JSON, otherwise `String`) ([`MacroEngine.js:332-348`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroEngine.js:332)); the env's `postProcess` function is applied to each individual macro result, not to the whole document ([`MacroEngine.js:220-227`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroEngine.js:220)). **Handler output is never re-scanned** — expanding `{{newline}}` inside a handler result is the handler's job via `resolve()`.
8. **Post-processors** run after the whole document: unescape braces, remove `{{trim}}` with its surrounding newlines, strip stray `else` markers ([`MacroEngine.js:299-323`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroEngine.js:299)).

The docs describe the same nesting direction: “Inner macros are resolved first” ([Macros §Nested Macros](https://docs.sillytavern.app/usage/core-concepts/macros/)). A handler's `resolve(text, { offsetDelta })` re-enters `MacroEngine.evaluate` with the same env and a context offset ([`MacroRegistry.js:453-455`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroRegistry.js:453)).

### Handler contract, registry, and extension API

A macro definition is registered with `MacroRegistry.registerMacro(name, options)`; options include `aliases`, `category`, `unnamedArgs` (count or definitions with `optional`/`type`/`defaultValue`), `list` (boolean or `{min,max}`), `strictArgs` (default `true`), `description`, `returnType`, `displayOverride`, `exampleUsage`, `delayArgResolution`, and a required synchronous `handler` ([`MacroRegistry.js:62-76`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroRegistry.js:62), [`MacroRegistry.js:484-680`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroRegistry.js:484)).

The handler receives a `MacroExecutionContext` ([`MacroRegistry.js:104-130`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroRegistry.js:104)): `name`, `args`, `unnamedArgs`, `list`, `namedArgs` (always null), `flags`, `isScoped`, `raw` (inner text with nested macros resolved), `rawOriginal` (full `{{...}}`), `rawArgs`, `env`, `cstNode`, `range`, `globalOffset`, plus helpers `normalize`, `trimContent`, `resolve(text, {offsetDelta})`, and `warn(message, error)`. Handlers are **synchronous only**; the extension docs state “Handlers will run synchronously, so they can never return a `Promise`” ([UI Extensions §Registering custom macros](https://docs.sillytavern.app/for-contributors/writing-extensions/)). Legacy `MacrosParser.sanitizeMacroValue` explicitly warns and returns `''` for Promises ([`macros.js:279-307`](D:/Projects/SillyTavern/public/scripts/macros.js:279)).

Extension access is `SillyTavern.getContext().macros` ([`macro-system.js:44-59`](D:/Projects/SillyTavern/public/scripts/macros/macro-system.js:44), [`st-context.js:244`](D:/Projects/SillyTavern/public/scripts/st-context.js:244)): `register`, `registerAlias`, `registry`, `envBuilder`, `engine`, `lexer`, `parser`, `cstWalker`, `category`. Docs also show `macros.registry.unregisterMacro(name)` and `macros.registerAlias('greet', 'hello', { visible: true })` ([UI Extensions §Registering custom macros](https://docs.sillytavern.app/for-contributors/writing-extensions/)).

Registry behaviour: re-registering an existing name overwrites it and logs a registration warning; aliases are separate lookup entries pointing at the primary definition ([`MacroRegistry.js:301-319`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroRegistry.js:301)). `getPrimaryMacro` resolves aliases ([`MacroRegistry.js:364-368`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroRegistry.js:364)). Registration validates names, alias rules, argument definitions, list bounds, types, and `displayOverride`/`exampleUsage` brace wrapping ([`MacroRegistry.js:487-649`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroRegistry.js:487)).

The environment ([`MacroEnv.types.js:57-66`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroEnv.types.js:57)) carries `content` (the full input string) and `contentHash`, `names` (`user`, `char`, `group`, `groupNotMuted`, `notChar`), lazy `character` card fields, `system.model`, `functions.original` (a one-shot function that returns the original message once per evaluation) and `functions.postProcess`, `dynamicMacros`, and an open `extra` record ([`MacroEnvBuilder.js:81-175`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroEnvBuilder.js:81)). Extensions and other modules can augment it across an ordering scale through `envBuilder.registerProvider(provider, order)` ([`MacroEnvBuilder.js:36-72`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroEnvBuilder.js:36), [`MacroEnvBuilder.js:162-172`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroEnvBuilder.js:162)).

**Dynamic macros** (`substituteParams(..., { dynamicMacros })`, the old `substituteParamsExtended`) can be a string, a synchronous handler, or a full options object; they override registered macros for that evaluation and match case-insensitively ([`MacroEngine.js:173-213`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroEngine.js:173)).

### Where the engine runs during prompt assembly

`substituteParams` is called from 80+ sites; the prompt-relevant order is:

- **Prompt-manager definitions** are expanded when the prompt collection is built: `getPromptCollection` calls `preparePrompt`, which runs `substituteParams` on each definition with `original` only for the main/jailbreak replacements ([`PromptManager.js:1277-1289`](D:/Projects/SillyTavern/public/scripts/PromptManager.js:1277), [`PromptManager.js:1516-1536`](D:/Projects/SillyTavern/public/scripts/PromptManager.js:1516), [`openai.js:1479-1502`](D:/Projects/SillyTavern/public/scripts/openai.js:1479)).
- **Character-card fields** are expanded lazily on read via `baseChatReplace` → `substituteParams(..., { replaceCharacterCard: false })`, so card fields do not recursively expand card macros ([`script.js:3281-3291`](D:/Projects/SillyTavern/public/script.js:3281), [`script.js:3342-3407`](D:/Projects/SillyTavern/public/script.js:3342)).
- `scenario_format`/`personality_format`/group nudge/impersonation prompts are expanded during Chat Completion assembly ([`openai.js:1358-1362`](D:/Projects/SillyTavern/public/scripts/openai.js:1358)).
- Because the env is rebuilt from live globals on every `substituteParams` call, macros observe chat state at call time; there is no single global “expand the assembled prompt once” pass. The last expansion for message text happens immediately before a message is sent ([`script.js:5815-5825`](D:/Projects/SillyTavern/public/script.js:5815)) and at other send/generate bindings ([`script.js:8090-8094`](D:/Projects/SillyTavern/public/script.js:8090)).

### Integration constraints from DitzyTavern architecture

- **Server-authoritative** (ADR-0002): the engine must run server-side; browser-only macros cannot be reproduced.
- **SQLite authoritative state** (ADR-0005, amended by ADR-0024): variables would be new authoritative state and need tables/migrations, not browser storage.
- **Pure Prompt Compiler** (ADR-0014, superseded by ADR-0032): `compilePrompt` never touches SQLite/HTTP and is synchronous ([`compiler.ts:126-192`](D:/Projects/DitzyTavern/src/server/prompt-compiler/compiler.ts:126), [`index.ts:1-3`](D:/Projects/DitzyTavern/src/server/prompt-compiler/index.ts:1)). The Generation Plan seam is also pure ([`generation-plan/compiler.ts:10-14`](D:/Projects/DitzyTavern/src/server/generation-plan/compiler.ts:10)).
- **Budget compiles repeatedly.** `budgetPromptPlan` calls the `compile` callback to rebuild the plan for every omission candidate, including a binary search over history removal ([`budget.ts:121-151`](D:/Projects/DitzyTavern/src/server/prompt-compiler/budget.ts:121)). Any side-effecting (`setvar`, `incvar`) or nondeterministic (`random`, `roll`, `time`) macro evaluated inside `compilePrompt` would run several times per attempt with different results. `{{pick}}` in SillyTavern is deterministic precisely because of position hashing ([`core-macros.js:388-405`](D:/Projects/SillyTavern/public/scripts/macros/definitions/core-macros.js:388)), but `{{random}}`/`{{roll}}`/`{{time}}` are not.
- **Warnings are a plan field** `{block, macro}` ([`conversation-schema.ts:90-101`](D:/Projects/DitzyTavern/src/shared/contract/conversation-schema.ts:90)); richer diagnostics (arity/type) would need a shape extension.
- **Openings are expanded once at conversation creation** and persisted as final text ([`create.ts:249`](D:/Projects/DitzyTavern/src/server/conversation/create.ts:249)); SillyTavern expands greetings at generation time.
- **One shared processor** is an explicit commitment: compiler, preset editor, importer all consume `prompt-macros.ts` so they cannot drift ([`prompt-macros.ts:1-9`](D:/Projects/DitzyTavern/src/shared/prompt-macros.ts:1)). A new engine has to keep a stateless validation path for the client editor, which cannot construct server runtime state ([`PromptPresetRecipeRow.tsx:29-32`](D:/Projects/DitzyTavern/src/client/workspace/prompt-preset/PromptPresetRecipeRow.tsx:29)).
- **ADR-0036** commits to retaining `{{self}}`/`{{other}}`, mapping imported `{{user}}`/`{{char}}`, keeping unknown macros raw with a small editor warning, and supporting Prompt Comments in authored text ([ADR-0036](D:/Projects/DitzyTavern/docs/adr/0036-introduce-prompt-presets-as-assembly-recipes.md)).

## Narrow recommendation

**Build the language; adapt the catalogue.** SillyTavern’s engine is browser-coupled (DOM, `SillyTavern.getContext()`, chevrotain, moment, seedrandom, droll) and ~half its catalogue reads state DitzyTavern does not have, so neither vendoring `MacroEngine.js` nor claiming “full support” verbatim is realistic. The grammar is small enough for a hand-written lexer + recursive-descent/Pratt parser in TypeScript; this mirrors the observable pipeline (document scan → nested argument resolution → handler dispatch → no re-scan) without chevrotain or browser globals.

Concretely:

1. **Seam:** replace the internals of `src/shared/prompt-macros.ts` with a grammar module (tokens, identifiers, `::`/legacy `:`/space args, flags, scoping, variable shorthand) plus a stateless `validate`/`scan` path, and add a registry-backed engine under `src/server/prompt-macros/` that the Prompt Compiler imports. Keep `scanMacroToken` semantics for the SillyTavern importer’s `user`/`char` translation, or reimplement it on the new lexer.
2. **Purity:** pass the macro environment as explicit data into `compilePrompt`; handlers are synchronous value functions. No SQLite or DOM inside the engine.
3. **Budget collision:** expand macros **once per Generation attempt before budgeting**, or memoize per (block text, environment, variable snapshot), so the binary-search recompiles in `budget.ts` reuse frozen text. Never re-run side-effecting macros per candidate.
4. **Variables:** server-owned SQLite tables (global scope and per-Conversation scope, per ADR-0005) behind a small read/write interface. Compilation reads a snapshot and journals writes; the attempt commits the journal once after the final plan is chosen, in recipe order. This reproduces SillyTavern’s document-order `setvar` → `getvar` threading without making the compiler impure.
5. **Catalogue phasing.** P1: grammar, registry, `self`/`other`, utility (`space`, `newline`, `noop`, `trim`, `reverse`, comments), time, `random`/`pick`/`roll`. P2: `if`/`else`/scopes/`#`, variable shorthand and all local/global variable macros. P3: chat/env/card macros as the corresponding server state arrives. Macros with no server counterpart (`input`, `firstDisplayedMessageId`, `outlet`, instruct/system-prompt/authors-note/summary/model/token-limit/extension/`isMobile`, image prefixes, `banned`) stay unknown and raw.
6. **Warnings:** match SillyTavern for unknown macros (keep raw; no warning) or keep the existing editor-only warning as a product choice; add arity/type failures to the plan warning shape only if the product wants them surfaced. The current `{block, macro}` record is too narrow for argument-level diagnostics.
7. **Do not** port the four unimplemented flags (`!`, `?`, `~`, `>`) or named arguments; SillyTavern itself does not execute them.

## Uncertainty

- **Scoped comments do not do what the docs say at this commit.** The comment macro carries `list: true` ([`core-macros.js:292`](D:/Projects/SillyTavern/public/scripts/macros/definitions/core-macros.js:292)), and the scoped-pair gate refuses scoped content for list macros ([`MacroCstWalker.js:1312-1314`](D:/Projects/SillyTavern/public/scripts/macros/engine/MacroCstWalker.js:1312)). Every other source — the docs, the macro description, and DitzyTavern’s ADR-0036 — presents `{{//}}...{{///}}` as supported. No test covers the scoped form, and I did not execute the browser engine to confirm the literal output; the code path says both tags stay raw. Treat DitzyTavern’s existing scoped-comment support as compatible-or-better until SillyTavern behavior is confirmed empirically.
- **Docs/code drift elsewhere:** the docs list `no` as falsy but `isFalseBoolean` only accepts `off`, `false`, `0` ([`utils.js:1020-1022`](D:/Projects/SillyTavern/public/scripts/utils.js:1020)); the docs’ `{{charIfNotGroup}}` row (“empty in groups”) contradicts the alias registration ([`env-macros.js:30-36`](D:/Projects/SillyTavern/public/scripts/macros/definitions/env-macros.js:30)); the docs table includes extension macros and `{{reasoning*}}` that are only registered when their modules load.
- The docs claim the experimental engine is on by default for new installations; the pinned code still has a legacy path and a flag, and I did not verify default initialization order in this checkout.
- Chevrotain error-recovery edge cases (exact plain-text output for every malformed form) are asserted only by the e2e tests I sampled, not exhaustively.
- SillyTavern has no “expand the assembled prompt once” pass; `substituteParams` runs wherever a string is used, with live state. The full set of call sites and their ordering for every API backend was not traced.
- `/reroll-pick` and `chat_metadata.pick_reroll_seed` are referenced by the `pick` handler but the slash command itself was not inspected.
- Whether “full support” product intent includes extension-provided macros (`authorsNote`, `summary`, SD prefixes) is a product decision, not settled by the sources.
