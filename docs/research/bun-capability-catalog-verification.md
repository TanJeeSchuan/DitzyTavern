# Bun documented capability catalog: verification

Audited 2026-10-25 against Bun's live documentation index and the official Bun 1.4.4 release article. The installed runtime, package manifest, and Docker stages are reported as 1.4.4 in the existing repo audit. This document verifies documentation coverage and identifies gaps; it does not map application call sites or claim performance gains.

## How to read the catalog

The official [`llms.txt`](https://bun.com/docs/llms.txt) is a navigation index, not a versioned API contract. The docs site can describe APIs added after an installed release. Treat each item as a documented capability family, then check the 1.4.4 release notes, local runtime, and local type declarations before proposing adoption. The versioned [Bun 1.4.4 release article](https://bun.com/blog/bun-v1.4.4) is the source for that release's changes. Its benchmark figures are upstream results and do not predict DitzyTavern performance.

## Verification against the two existing audits

The existing `bun-1.4.4-feature-audit.md` follows the 1.4.4 release article's feature headings; `bun-ecosystem-audit.md` adds broad runtime, ecosystem, build, and testing coverage. The documentation-family coverage is broad, but their application findings were captured at commit `52b9c25c` and need to be checked against current HEAD `5c33cd12` before reuse. This catalog verifies sources and family coverage; it does not certify those old source-to-repo mappings. These clarifications prevent overclaiming:

- The docs index is current and unversioned. It includes entire first-party API families such as native Redis and S3, but listing them says nothing about whether every documented option is present in the installed 1.4.4 binary or matching `@types/bun` declarations. Verify with the local runtime and types before planning code.
- The official 1.4.4 article confirms `bun fmt`, `bun check`, package-install changes, SQL and SQLite changes, WebSocket changes, runtime improvements, `Bun.Glob` updates, and dev-server overlay work. Its performance figures are Bun's benchmarks; do not translate them into application speedups.
- For SQLite, the release article specifically advertises user-defined functions and update hooks. The repo audit's distinction is important: a row-level hook does not inherently replace transaction-aware domain events, and a JS callback in SQL has a different cost/contract from a SQL-native operation.
- Current docs include TypeScript 6/7 declaration guidance. This is relevant to declaration setup, but is not proof that simply upgrading declarations is safe with the installed compiler; the repo's typecheck remains the arbiter.
- The older ecosystem audit proposes an `ArrayBufferSink` accumulator as a candidate. The current [profile report](bun-arraybuffer-sink-profile.md) benchmarks it against production-derived payloads and rejects it: no measurable single-request advantage and regressions in concurrent large embedding cases. Do not carry that proposal forward. The report also supersedes the older embedding-array representation claim: current `embedding.ts` returns `Float32Array` views and cosine accepts `ArrayLike<number>`.
- The existing catalog mentions S3/Redis and many advanced APIs. Their omission from the shorter 1.4.4 release-feature table is appropriate when they were not new in that release.

## Especially promising, bounded follow-ups

1. **`bun fmt`**: the clearest documentation-to-repo tooling gap. Choose settings and inspect the actual diff before enabling a gate; this changes source formatting, not application runtime behavior.
2. **CI/package cache reuse**: official package-manager facilities include `bun pm fetch` and cache operations. The existing audit already notes that Docker's manifest-first layer is cached; focus on CI job boundaries where downloads repeat. Measure pipeline time before and after.
3. **Bun diagnostic tooling**: CPU profiles and heap snapshots are a low-dependency way to answer a concrete performance/memory question. They require a target symptom and representative workload; none is established by this catalog.
4. **Native APIs when touching matching code**: `Bun.SHA256.hash` and `Bun.Glob` have narrow roles. SHA-256 is not `Bun.hash`; native glob adoption should preserve match semantics and error behavior. These are opportunistic edits, not project-wide rewrites. The earlier `ArrayBufferSink` proposal is rejected by the newer production-derived profile.
5. **SQLite UDFs/aggregates**: worth considering only if a repeated SQL-side computation emerges. `Database.function()`/`aggregate()` make the capability concrete; the code still needs a domain-level reason to execute custom JS from SQL.

There is no evidence here for adopting PostgreSQL/MySQL, Redis, S3, Workers, a Bun bundler migration, a new auth system, or a standalone executable. Each introduces machinery; the existing audits correctly make those conditional on product or operational requirements.
