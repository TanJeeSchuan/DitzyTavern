# Paint Illustrations through a built-in Paint panel

Writers can have an Image Model paint an Illustration of a moment in a Chat. This supersedes the image-generation exclusion in [ADR-0001](0001-focused-reimplementation.md) and [ADR-0046](0046-admit-images-natively.md). The writer starts every painting. Automatic painting, chat models that reply with pictures, and local diffusion backends stay excluded.

Painting is built in, not a Box, which departs from [ADR-0050](0050-build-story-features-as-boxes.md). An Illustration keeps no story state and contributes nothing to a Generation. As a Box it would have needed three additions to the contract for one consumer: a paint capability, a background job that needs neither a Decision Model nor a delegate agent, and a surface inside the story view. Lorebooks are the precedent for a built-in feature with its own Prompt Preset slot. A Box that needs pictures, such as Sprites (#234), gets a paint capability when it is built.

The writer paints from a Paint panel: an optional Ask, a Brief, reference pictures, then the painting. Two other designs were rejected. Having the story model request pictures with a tag in its reply reaches only replies written after the feature is on, so Openings, older passages and imported Chats could never be illustrated, and it spends every story model's output on a format it must obey. Sending the passage itself as the Brief needs no model call, but image models that expect a short description handle long prose badly, and the writer cannot point at a moment in words.

A model writes the Brief from the Ask through a Paint Preset, a Prompt Preset the Chat selects apart from the one its Generations use. A built-in minimal one is the default, so painting works in a Chat whose story preset was imported and has no Brief instruction, and no roleplay instruction competes with the request. The cost is that a Brief request shares no provider cache with the story, so it reads only the last five Messages by default. The Brief instruction is a preset slot sent only when a Brief is written, which lets one preset serve Generations and Briefs when the writer prefers that. A Brief request includes Lore, where characters outside the Cast are described, and runs no Boxes, because running them would simulate story state for a request that writes no story.

How a character looks is a sixth Prompt channel, Appearance, holding description text with Image References in it. A separate list of pictures with captions was rejected: a channel already has the editor, the copy into a Participant, Save as Character, Fork, the orphan sweep and the Image Anchor fallback for Text-only Models. Whether models receive its Images is a switch in the Definition, so the Character holds the default and each Participant's copy is that Chat's override, with no override layer. The Portrait stays out of Appearance unless the writer inserts it, keeping ADR-0046's rule. A writer can ask a model to describe a picture into Appearance. That does not revive the describe-once captioning ADR-0046 rejected: the writer asks for it, the result is text they edit, and models that can see still receive the picture.

An Illustration belongs to the Variant it was painted from and is not a Message. As a Message it would become the final Message and stop the last reply from being swiped directly, every reader of Messages would have to skip it, and it would be Conversation history, which is the cost in prompt cache and vision tokens this design avoids. An Illustration never enters a Prompt Plan; the writer who wants a model to see one adds it to their next Message as an Image Reference. While it is being painted it is provisional, held in server memory, and nothing else in the Chat treats it as existing. Once painted it is stored as per-Variant data, so Fork, Trim Variants, Variant deletion and the orphan sweep need no change, and it lands without advancing the Conversation Revision, as a Box's background record does.

The Image Model is a model role on a new `images` API Format, called through the AI SDK's `generateImage`, with OpenRouter's Image API as the first wire. Sending image output through the Chat Completions `modalities` field was rejected because it would put pictures in the streaming story client and reverse ADR-0015. One Image Model and one model for describing pictures are selected for the whole app, as Decision Models are.
