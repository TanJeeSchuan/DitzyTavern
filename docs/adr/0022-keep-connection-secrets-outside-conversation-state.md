# Keep connection-secret plaintext outside Conversation state

A Connection Secret is server-owned application configuration, not Conversation data. It includes both a Connection Profile's dedicated API credential and every user-configured request-header value; a JSON header key may be visible while its stored value remains secret. Version one stores one encrypted secret payload per Connection Profile containing its dedicated credential and custom-header values. The application-managed `CONNECTION_SECRET_KEY` is exactly 32 cryptographically random bytes represented as Base64. An explicitly injected environment or deployment-secret value takes precedence. When the variable is absent on first local startup, the backend generates the key and writes `CONNECTION_SECRET_KEY` to the Git-ignored `.env` file for later startups. An explicitly present but malformed value is a configuration error and is never silently replaced. If the key cannot be generated or durably written, startup fails before the server accepts work and reports a descriptive error identifying the failed master-key bootstrap without printing key material. The key is never stored in SQLite, printed, returned to the client, or supplied by a model provider. It encrypts external-provider credentials; it is not itself a provider credential or a per-Profile override. Passphrase derivation and user-authored master-key passwords are outside version one.

A Connection Secret's plaintext is never copied into exports, snapshots, SSE events, logs, Prompt Plans, Generation Settings, or Variant settings records. Every encryption of the Profile payload uses a unique cryptographically random 12-byte nonce, a 16-byte authentication tag, and authenticated additional data binding the ciphertext to its schema version and stable Profile identity. The database retains an encryption format version and key identifier beside the nonce, ciphertext, and tag. Secret changes atomically decrypt, modify, and re-encrypt the whole Profile payload. Decryption fails closed when the master key is absent or malformed or authentication fails; the backend never silently clears or replaces ciphertext in response.

The dedicated credential is handled like a password: Profile creation may include its initial value atomically, after which the client sees only whether one is configured. Separate Set or Update and confirmed Reset actions replace or remove it without ever returning the stored value; ordinary Profile Apply cannot touch it. Preset plus API Format define how a compatible Model Backend applies that opaque credential, without exposing general header-name or prefix fields. The custom-header editor separately receives a safe JSON projection whose keys and configured states are visible while values remain redacted; it accepts explicit `keep`, `replace`, and `remove` operations and is the escape hatch for nonstandard authentication. A client-side JSON editor operates only on that projection and new replacement drafts—redaction is not performed by sending a real secret to the browser and hiding it in the DOM.

This encryption protects a copied database or backup whose thief does not also possess `CONNECTION_SECRET_KEY`. It does not protect secrets from a compromised backend process or host that can read both the key and ciphertext. Losing or replacing the master key makes existing Connection Secrets unrecoverable; the user must reset those credentials. Version one records an encryption format version but implements no key-rotation workflow, multiple-active-key scheme, or master-key export/import UI. Deployment operators back up their injected secret, while local installations must back up `.env` with the database. Key provisioning and recovery must not be obscured by the redacted client UI.

URL query parameters are not Connection Secrets. They remain visible to the client and are neither detected nor redacted as possible credentials; users who place sensitive material there accept that exposure boundary.
