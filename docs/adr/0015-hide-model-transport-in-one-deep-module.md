# Hide model transport in one deep Model Client module

Model transport will live behind a deep Model Client interface that accepts a provider-neutral Prompt Plan and returns an asynchronous stream of normalized model events. Its implementation directly owns the version-one OpenAI-style REST request translation, credentials, streaming parser, cancellation, errors, and optional usage reporting.

The Model Client may satisfy that interface through multiple internal Model Backend adapters. Connection Profiles expose an advanced `Automatic` or concrete Backend preference, but Workflows and Conversations never depend on Backend-specific types. Version one ships only the AI SDK Backend, so `Automatic` resolves to AI SDK; Native and other Backends remain deferred until a concrete incompatibility justifies them. `Automatic` resolves one compatible Backend before the outbound request starts and never falls through to another Backend after a request has begun. Every Backend must preserve the shared contract for visible Content streaming, supported Reasoning Content streaming, cancellation, no automatic retries, stream-inactivity timeout, normalized finish and error outcomes, arbitrary model IDs, and advisory model discovery. A Profile using unsupported Backend-specific options cannot switch to that Backend.

The AI SDK Backend exposes an advanced AI SDK Adapter selected from a closed set compiled into DitzyTavern. An Adapter is a stable application concept that selects and configures one bundled AI SDK provider package; its persisted identifier never contains an npm package version, package path, or dynamically loaded code. Version one bundles OpenAI Compatible, DeepSeek, and OpenRouter Adapters. Unlike Model Backend, AI SDK Adapter has no `Automatic` value. A Connection Preset copies a concrete recommended Adapter into the new Profile, after which it remains explicit and independently editable. Editing the request URL never silently changes the Adapter. Version one exposes no arbitrary Adapter-options JSON; request-body extensions use API-Format Request Overrides and transport extensions use Profile headers until a concrete feature justifies a typed Adapter option.

If a saved Profile names an Adapter unavailable in the running application version, the Profile remains preserved but unusable and reports an explicit Adapter-unavailable error. The Model Client never silently substitutes OpenAI Compatible or another Adapter.

Connection Profiles own API Format, request URL, credentials, headers, timeouts, output-token representation, and discovery configuration independently of their selected Backend. Version one implements only OpenAI Chat Completions. OpenAI Responses and Anthropic Messages remain reserved API Format vocabulary but are unavailable until their distinct request and stream shaping rules are designed; neither is treated as Chat Completions merely because an endpoint accepts similar inputs. Only genuinely Backend-specific switches live in namespaced Backend Options. Changing Backend therefore preserves the shared connection details instead of silently selecting another endpoint, Format, or credential.

The request URL field has one deterministic shorthand. When its parsed pathname ends in `/`, it is a base URL and the Model Client appends the selected Format's standard operation path; for the implemented Chat Completions Format that path is `chat/completions`. When the pathname has a non-empty final segment, the URL is an exact request URL and remains unchanged, supporting nonstandard paths such as `/generate`. Presets fill the Format and URL together, and the UI shows the resolved request URL before Apply. The selected Backend must honor that resolved URL rather than substituting its own provider path.

Request and Models URLs accept only `http:` and `https:`. Loopback and private-network destinations remain valid so local and LAN model servers work. URL user information, fragments, and other schemes are rejected. Query parameters remain ordinary client-visible Profile configuration; version one performs no credential-pattern detection, warning, or query-secret redaction. The user is responsible for not placing secrets there. Model Client requests do not follow redirects: a redirect is reported as an error so credentials and custom headers are never automatically forwarded and the saved resolved URL remains the actual destination.

For OpenAI Chat Completions, version one treats the streaming contract as a first-class protocol rather than treating OpenAI's hosted service as a privileged provider. Generation settings include a model identifier, ordinary sampling and token parameters, and an extra JSON body object.

For Chat Completions, Request Overrides are merged late. Extra body fields may override ordinary generation parameters such as `temperature` and `top_p`, and may contain unknown provider-specific fields. They may not override the structural `messages`, `model`, `stream`, `n`, `max_tokens`, or `max_completion_tokens` fields. The Conversation's editable response budget is the single source used by both Prompt Compiler reservation and Model Client output-token translation. The Model Client forces `n: 1` so one Generation always produces exactly one Variant. It also rejects tool-calling fields, audio, and non-text modalities that version one cannot represent. Textual response formatting, including JSON mode, remains allowed. Custom header names must be valid HTTP header tokens and are unique under case-insensitive comparison while preserving display casing. They may replace `Authorization` to support alternate authentication and routing schemes, but the Model Client rejects transport-owned headers such as `Host`, `Content-Length`, and `Transfer-Encoding`.

The Model Client receives one provider-neutral response budget. In automatic mode each Backend translates it through the selected API Format; the AI SDK Backend uses its common `maxOutputTokens` setting and Native must produce equivalent wire behavior. Chat Completions Profiles may explicitly select `max_tokens`, `max_completion_tokens`, or `omit`. An explicit key changes only the emitted representation. `omit` retains local Prompt Compiler budgeting while leaving the remote output limit unspecified, and Request Overrides cannot independently supply any format-owned output-limit key. Output-limit mappings for deferred Formats remain unspecified.

The Model Client also receives the Profile's opaque dedicated credential. Preset plus API Format determine its standard authentication meaning: the AI SDK Backend delegates ordinary placement to the selected provider package, and Native must reproduce equivalent behavior. Version one exposes no general credential-header-name or value-prefix fields. Nonstandard authentication belongs in write-only custom headers, which may replace the standard header, and a Profile using only custom authentication may omit its dedicated credential.

The Model Client may fetch model IDs only from an explicitly configured exact Models endpoint URL using the common `GET` response shape `data[].id`. It reuses the configured credentials and headers, normalizes failures for display, and does not make successful discovery a precondition for generation. A successful refresh replaces the Profile's persisted Discovery Catalog, while failure preserves it without introducing refresh history or stale-state metadata. The cache is separate from editable Connection Settings and does not participate in their revision. Without a Models URL Refresh is unavailable, but model IDs remain arbitrary user-entered strings.

The Chat Completions translation uses only the broadly compatible `system`, `user`, and `assistant` message roles. It emits one initial `system` message containing System Instruction, both active Participants' Identities, and Scenario in the Prompt Plan's named-block order; then Example Dialogue; then selected Conversation history with roles derived from current Control; and finally a `system` message containing Post-History Instruction. Historical speaker names are already embedded textually by the Prompt Compiler, so the transport does not depend on the optional API `name` field. It intentionally does not emit the newer `developer` role.

Each implemented API Format must preserve the Prompt Plan's complete block content, internal named order, speaker and history order, and authorship meaning, but may place those semantics into the Format's native system, instructions, and message structures. Wire-level JSON placement need not be identical across Formats. Both OpenAI Responses and Anthropic Messages shaping are deferred entirely.

The Model Client never automatically retries a failed request. One outbound request is exactly one Generation attempt. A failure before any visible Content or Reasoning Content removes the empty provisional Variant and restores the prior selection; a failure after either kind of output persists the Variant as interrupted. Starting another Variant is the user's explicit retry action, preventing hidden duplicate requests and charges after ambiguous transport failures.

For an upstream HTTP failure, the Model Client first attempts to extract and sanitize a conventional provider error message. If that is impossible, it falls back to returning at most the first 16 KiB of an upstream textual or JSON response body for user diagnosis and marks truncation explicitly. For binary or unsupported media types it reports status, media type, and byte length instead. Response headers, request bodies, credentials, and configured custom-header values are never included in the client error. Raw upstream failures are not logged by default.

Each request has a configurable stream-inactivity timeout, defaulting to 120 seconds and allowing the user to increase or disable it. There is no total-duration timeout while the stream remains active. Any syntactically valid SSE activity resets the timer, including visible text deltas, reasoning or thinking deltas, usage events, and keepalive comments. Arbitrary partial transport bytes do not. A timeout cancels only that Generation and follows the ordinary interruption rule: a Variant containing visible Content or Reasoning Content persists as interrupted, while a slot containing neither is removed.

When an endpoint and selected Backend expose a recognized separate textual reasoning stream, the Model Client normalizes it as Reasoning Content. The server synchronizes and persists it separately within the Variant, and the client presents it as collapsible output. Reasoning Content counts as reply output for Variant durability even if no visible Content arrives. An unrecognized provider-specific reasoning shape does not fail an otherwise valid Generation: visible answer Content continues and separate reasoning is omitted. Version one does not include Reasoning Content in later prompt messages. That is a deliberate deferral rather than a permanent exclusion: future tool-call support may need to return reasoning according to the endpoint's concrete multi-turn contract.

The Model Client normalizes a provider `finish_reason` of `length` as a `length-limited` terminal outcome while retaining the raw finish reason in compact metadata. The Conversation persists that Variant and remains immediately usable; version one does not automatically request or append a continuation.

Version one will not build a public provider-adapter interface, inheritance hierarchy, or general provider registry. Model Backend adapters and their compatibility checks remain private to the Model Client; the user-visible Backend preference does not expose an SDK interface to the rest of the application.
