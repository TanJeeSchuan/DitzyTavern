# Use SillyTavern syntax for Prompt Macros

DitzyTavern will preserve SillyTavern macro syntax and documented behavior for an explicitly supported subset, with named DitzyTavern differences, rather than inventing a separate template language. This keeps supported imported expressions familiar and avoids translation into another authoring language. The contract does not promise bug-for-bug parity or support for every SillyTavern macro.

The existing participant mapping and Prompt Comment decisions in [ADR-0036](0036-introduce-prompt-presets-as-assembly-recipes.md) remain in effect. Supported syntax follows the researched SillyTavern contract except for the explicit DitzyTavern differences recorded here and in ADR-0038.

Macro registration will initially be internal and straightforward for developers with code access. A public extension API is deferred; the internal registration mechanism should provide a place to add handlers without editing parsing logic. This does not commit to plugin loading or a stable external handler contract.

Use one project-owned scanner and recursive parser for the supported SillyTavern syntax. It produces the evaluator's syntax tree directly, including nested arguments and paired scopes. A parser framework was rejected because the language still required custom delimiter balancing, header parsing, and scope pairing around the framework grammar. Do not add Handlebars: its argument and subexpression syntax would require translating between languages without removing the need to implement DitzyTavern's evaluation rules.

Support persistent Macro Variables scoped to Conversation and Prompt Preset through `setvar` and `getvar`, preserving values between Generations rather than redefining these names as temporary assignments. Blocks within an assembly share variable values, so later reads observe earlier writes. Retention, preset isolation, and state derivation follow ADR-0038's Variant rules, which intentionally differ from SillyTavern's single shared local-variable store.

Sibling Variants evaluate variables from the state before their target Message, not from another sibling's resulting values. Only selected Variants affect the Macro State used by future generations, as specified in [ADR-0038](0038-carry-macro-state-through-selected-variants.md). This intentionally differs from repeatedly mutating one Conversation-wide variable store on each swipe.

Existing macro-enabled Participant Definition fields share the active Conversation + Prompt Preset variable scope with the rest of the assembly; there is no separate Character-owned variable store. Expand an opening once when the Conversation is created, retaining its final text and recording its writes with the greeting Variant under the preset selected at creation. Later preset switches neither rerun that opening nor transfer its variables into another preset's namespace. Each preset must initialize the values it needs.

Each Generation attempt, including a Sibling Generation, assembles from the current preset, Participant Definitions, and relevant history. Prompt-affecting edits apply to subsequent attempts; already captured prompts stay fixed. This retains ADR-0009's per-attempt assembly behavior instead of freezing prompt inputs across sibling Variants.

`roll` and `random` sample afresh for each attempt. `pick` remains deterministic for the same Conversation, preset, source text, and macro position; changes to its source or choices may change its result. Expansion and dependent variable reads remain consistent throughout an attempt's budget calculations and send. Expand enabled authored blocks once in recipe order, including each enabled duplicate occurrence, and reuse their text and writes while budgeting removes literal history entries. Disabled blocks do not execute. This is a design requirement for the new macro engine, not a claim that the current processor supports these macros.

Capture one timestamp for each assembly. Local time/date macros use the initiating client's timezone and locale, with explicit macro timezone arguments taking precedence. Budget calculations and sending reuse that captured clock. The same rule applies when creating an opening; inspecting or refreshing a plan is an explicit assembly and may capture a new clock.

Generating from an inspected Prompt Plan preserves the exact expanded text, including sampled macro results and manual edits. Generating must not silently reroll an inspected result. Explicitly refreshing the preview may produce new rolls. Invalidate a preview when its canonical captured Generation Preparation changes, including selected history, the controlled Participant Definitions, active preset, Generation Settings, and variable input. Refresh is cheap, so the implementation does not maintain a second field-level model of which compiler inputs happen to matter to one recipe. Unrelated Cast additions, background Variant completion, and elapsed time alone do not invalidate it. Inspection by itself does not persist pending variable writes; they follow the Variant lifecycle when the inspected plan is used for a Generation.

The inspected Prompt Plan is a direct edit of the input for one Generation. After inspection edits, do not run macro expansion again or infer variable changes from the edited text. The writes recorded during the original expansion remain unchanged. For example, replacing the text "Rolled 7" with "Rolled 18" changes the model input but does not change an expansion-time `rollResult = 7` assignment. Macro-looking text manually inserted into the expanded plan is transmitted literally. Existing structural and context-limit validation still applies under ADR-0021.

The first supported catalogue covers nested arguments, conditionals and scoped content, Prompt Comments and text utilities, Conversation-variable operations, dice/random/pick, time/date, and existing participant macros. Global variables and additional SillyTavern integrations are deferred. Unsupported expressions retain the existing raw-text and warning behavior. See the [scope notes](../research/prompt-preset-macro-usage.md#accepted-initial-scope-and-deferrals) for the deferred groups.

Do not execute macros in model-produced text, either on receipt, display, or later history replay. The user plans a tool call for memory updates; that separate mechanism is outside this macro-engine implementation. Prompt-authored examples of macro syntax still require escaping.

Variable writes follow existing Variant retention, including interrupted or failed attempts with retained output, as specified in ADR-0038. Acceptance-time mutation of one shared variable store was rejected. See the [source research](../research/sillytavern-macros.md) for the existing engine and integration constraints, and [sample preset findings](../research/prompt-preset-macro-usage.md) for concrete variable and dice usage.
