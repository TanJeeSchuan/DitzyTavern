# Apply configuration edits atomically

Configuration panels edit client-local drafts rather than mutating authoritative state per keystroke. Explicit semantic Apply actions send revisioned commands that validate and atomically replace a Character or Participant name, whole Prompt, or whole Openings list. Generation Settings and each global Connection Profile retain their own whole-object Apply actions. A Connection Profile draft includes its shared connection details, Model Backend preference, namespaced Backend Options, and explicit `keep`, `replace`, or `remove` operations for write-only custom-header values; changing Backend never silently swaps in another endpoint or credential. One accepted Apply commits the non-secret Profile and its header-secret operations as one Connection Settings revision. The entire global Connection Settings aggregate, including Profile activation, uses one revision counter rather than independent per-Profile revisions.

Connection Profile Apply performs structural validation and persistence only; it makes no network request. Endpoint reachability and credentials are checked only through a separate, optional Test Connection action so a temporarily offline or intentionally incomplete endpoint can still be saved. Test Connection exercises the form's current unsaved Profile draft without persisting, activating, or revising it. It may include explicit custom-header replacements, while redacted values use `keep`; the separately managed dedicated credential must already have been Set or Updated. Test Connection requires a model ID and executes one real minimal Chat Completions Generation requesting a short response with a small output budget, no automatic retry, and a short timeout. The UI warns that this contacts the external provider and may incur a charge. Its normalized result is transient and does not become a persisted Profile-validity state.

The dedicated credential is not part of later Profile drafts. Profile creation may commit its initial credential with the new Profile, but subsequent credential replacement uses a separate Set or Update action and removal uses a separately confirmed Reset action. Ordinary Profile Apply leaves it untouched.

Generations use only the last successfully applied configuration. A sibling Swipe started while a panel is dirty therefore cannot capture a half-edited Prompt, incomplete endpoint, or temporarily invalid JSON object; unsaved edits remain client-local and do not create authoritative revisions.

If another client changes the same Conversation before Apply, the expected-Revision check rejects the stale command. The client preserves the complete local draft and refreshed authoritative state for manual comparison or retry; version one performs no field-level automatic merge. Application-global Connection Settings, including Profile activation, use the same atomic replacement behavior with their own configuration revision.
