# DeepSeek Harness Creator Mode

Research snapshot: 2026-11-03. Source code was inspected at DeepSeek Harness commit [`ce7073d51254c26cd63b22a60835b8f948deb447`](https://github.com/deepseek-ai/deepseek-harness/commit/ce7073d51254c26cd63b22a60835b8f948deb447) and DitzyTavern commit `609df8eda09a3ecedf575e0f48d46a9c900e82c9`. DSH code links pin that revision. Local links refer to the inspected DitzyTavern checkout. This is source research, not a hands-on reproduction of the DSH demos or a generated-Box experiment.

## Recommendation

Add conversational Box authoring if the aim is to let writers invent mechanics and interfaces for their stories. Put **Create a Box** in the Box manager, with a separate authoring conversation and coding model. The useful part of Creator Mode is its complete authoring loop: discover the extension contract, write a native extension, build it, exercise it, install it, and revise it from feedback.

DitzyTavern already has the extension contract and runtime. Build on those. Importing Cordis, replacing the story Generation loop with a coding agent, or adding another plugin format would create unnecessary work. The strongest product advantage is that a generated feature can participate in story state, Swipes, and Prompt Plan inspection, rather than merely display a generated page.

## Findings

- **Creator Mode is an agent preset and an authoring workflow, not a separate visual editor.** The Web preset picker describes it as a mode that customizes DSH through conversation, writing plugins that add features/UI or combining tools and prompts into a new mode. The preset includes ordinary task tools, runtime inspection, authoring guidance, and `plugin_manager`. ([preset picker copy](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/client/ui-agent-preset/src/client/guide-locales.ts); [agent preset package](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/preset/agent-preset/README.md); [manager](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/boot/plugin-manager/README.md))
- **Runtime inspection is read-only and target-oriented.** `cordis_inspect_list` discovers providers; `cordis_inspect_query` returns exact methods/types and selected live config/schema/tool information. It does not call business methods, configure plugins, or execute generated code. Client-side inspection requires a connected page; profile Loader inspection does not enumerate plugins mounted only inside detached agent-preset trees. ([tool docs](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/extensions/tool-cordis/README.md))
- **The authoring loop is source/package based.** Guidance tells the agent to inspect the running APIs, read the installed package README and source, author a plugin/bundle and patch, install it into a profile, then inspect/apply and exercise it. Bundles are npm packages with a `dsh.bundle` manifest and Cordis patch; `dsh plugin add` or `plugin_manager.install_bundle` installs them. Local linked packages support iteration; rebuild/restart may be needed. ([plugin authoring/install guide](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/docs/user/develop/basic/publish.md); [Creator skill procedure](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/preset/agent-preset/skills/cordis-plugin-development/SKILL.md))
- **UI integration is through declared Client plugins and host-owned slots.** Plugin code registers React views into slots exposed by the current client; runtime introspection can discover slot APIs and props. Guidance rejects replacing the app root, injecting arbitrary DOM/iframes, or assuming layout around controls. ([UI authoring guidance](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/preset/agent-preset/skills/cordis-plugin-development/references/ui-plugin.md); [plugin practices](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/preset/agent-preset/skills/cordis-plugin-development/references/practices.md))
- **Installation is an explicit, privileged action.** The Web plugin page and the model tool share profile-level operations. Tool changes require full access or per-call approval. Installed Host plugin code executes in-process outside the workspace sandbox; package build scripts need separate permission. Git dependencies may run package code during `prepare` when allowed. ([manager security/operation contract](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/packages/boot/plugin-manager/README.md); [install guide security note](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/docs/user/develop/basic/publish.md))
- **DSH itself warns that it is not hardened for untrusted use.** It is developer-preview software, has not had a security audit, and can execute generated code/commands and load plugins with access to available files, credentials, processes, and network. Sandbox and approvals reduce risk but do not guarantee isolation. ([official safety notice](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/SAFETY.md); [README preview notice](https://github.com/deepseek-ai/deepseek-harness/blob/ce7073d51254c26cd63b22a60835b8f948deb447/README.md))
- **Demos are examples, not reproducibility evidence.** DeepSeek’s official prompt collection offers seven prompts, but explicitly says some showcased plugins were refined over several conversational rounds and one prompt may not reproduce the video result. Prompts include a theme changer, interactive 3D/educational content, and a conversation statistics plugin. ([official demo prompt collection](https://cdn.deepseek.com/harness/dsh-creator-mode-prompt-collection-en.html))

## Inference

The distinctive capability is a guided agent that can discover a host’s extension APIs, generate native plugins, and persist/install them with an approval boundary. It is not merely prompt preset authoring: generated code can change the running application and has host-level consequences. DSH’s implementation also couples authoring to its Cordis plugin model, package manager, profile/bundle configuration, and client slot API; these details are DSH-specific evidence, not a claim that the same architecture should be copied elsewhere.

## What DitzyTavern already supplies

The following are implemented capabilities, not proposed work:

- **A native extension unit.** Built-ins live in `src/boxes/<id>/`; installed Boxes live in `data/boxes/<id>/`. Both use the same descriptor, server hooks, client module, and SDK. The loader discovers folders and checks SDK major, schemas, identifiers, and hook combinations. A plugin cannot replace a built-in with the same id. ([loader](../../src/server/box/registry.ts), [Box contract and loading](../box-system/host.md#loading))
- **Interfaces integrated with the app.** Boxes can supply windows, primary panels, inspectors, settings, participant sections, and Generation trace views. The host provides launchers, a dock, error boundaries, and mobile window behavior. Client bundles share host React and SDK modules. The build checks that stylesheet selectors name the Box's own classes. ([client surfaces](../box-system/authoring.md#client-surfaces), [windows and dock](../box-system/host.md#windows-and-dock), [client builder](../../scripts/build-box-client.ts))
- **Story mechanics and state.** Moves attach actions to human Messages; `advance` contributes prompt items and optional records; `digest` reads settled prose; folds derive state from the selected Variants' effective records. The writer can override records. Box state can therefore follow Swipes without each generated plugin inventing its own history system. This still requires the author to choose correct record granularity: later records are not automatically recalculated after an earlier edit. ([records](../box-system/authoring.md#record-and-records), [generation lifecycle](../box-system/host.md#generation-lifecycle), [ADR-0050](../adr/0050-build-story-features-as-boxes.md))
- **Persistence and inspection.** Six storage scopes already exist. Box prompt items use preset placement and token admission; captured traces and final prompt text can be inspected. Creating a feature need not add a table or compiler branch. ([storage](../box-system/host.md#storage), [preset block](../box-system/host.md#preset-block), [advance](../box-system/authoring.md#advance))
- **An existing install path and test example.** `box:build` compiles a plugin client; copying its folder into the plugin directory and restarting loads it. The Tip Jar e2e describes installation, a user Move, its prompt contribution, and persisted state after restart. The test was read, not run for this research. ([installation](../box-system/authoring.md#install-a-plugin-box), [Tip Jar e2e](../../e2e/box-plugin.spec.ts))

These are a substantial foundation. The Box manager currently manages already-loaded Boxes per Chat; its Add action does not author or install new code. ([BoxManager](../../src/client/box-windows/BoxManager.tsx))

## What is missing

**An authoring agent.** The current model contract is a story-generation stream. Chat Completions request overrides explicitly reject `tools`, `tool_choice`, `functions`, and `function_call`; the Box `llm.complete` service supplies a text-completion interface, not a coding loop. A new system prompt alone cannot implement Creator Mode. A separate authoring runner needs file operations, build/check execution, diagnostic feedback, cancellation, and a session that can survive the app restart it requests. Reuse an existing coding runner for the first experiment; choosing an embedded runner is a later implementation decision. ([model input](../../src/server/model-client/types.ts), [unsupported fields](../../src/server/model-client/chat-completions.ts), [Box services](../../src/server/box/services.ts))

**A development workspace and build delivery.** Installed Boxes are currently authored in a checkout where SDK aliases and dependencies resolve. The production Docker image installs production dependencies and does not ship `scripts/`, the client source tree, or the Vite development toolchain. An in-app builder cannot assume that the deployed server has a working development checkout. A version-matched build workspace or separate build service is necessary for that deployment. ([install guide](../box-system/authoring.md#install-a-plugin-box), [Dockerfile](../../Dockerfile), [package scripts/dependencies](../../package.json), [typecheck inclusion](../../tsconfig.json))

**An install/revision workflow.** The server imports Boxes and mounts their routes at startup; the client imports its modules at startup too. The existing HTTP routes list Boxes, serve assets, and handle held values; they do not provide an authoring/install API. A productized flow must stage a complete candidate, validate it, and coordinate activation. An explicit restart is enough to prove the idea. Seamless live replacement would also need to handle mounted routes, running digests and Generations, client modules, and stored schemas; it is a separate engineering commitment. ([server loader](../../src/server/box/registry.ts), [Box routes](../../src/server/contract/boxes.ts), [client module loading](../box-system/host.md#client-modules))

**A clear code-execution boundary.** The server uses ordinary `import()` for both descriptor and server files, and some hooks receive the app database. Client code runs as a native module in the app page. SDK conventions, schema validation, and CSS checks do not sandbox it; imports execute before their exported values can be validated. Existing namespace helpers also do not authenticate the identity of their caller. A trusted local development workflow can use this model, but an automatically generated Box is executable code with app-level consequences. A disposable preview database alone does not isolate files or credentials: any isolated authoring/preview runner needs an actual process/container policy that withholds them. Installed Boxes remain trusted unless the execution architecture changes. ([dynamic imports and routes](../../src/server/box/registry.ts), [storage boundary](../box-system/host.md#storage), [client modules](../box-system/host.md#client-modules))

**Handling revisions that change data.** Startup already checks changed Box schemas, can discard invalid derived records, and holds incompatible writer-owned values for explicit clearing. Creator revisions must surface that result. An agent should not repeatedly rewrite schemas and silently clear story data to make installation pass. No new compatibility layer is needed; work within the existing schema-change behavior. ([checking stored values](../box-system/host.md#checking-stored-values))

## Proposed experience

This section is a design proposal, not existing behavior.

1. The writer chooses **Create a Box** from the Box manager and describes a mechanic: “Give this story an inventory. Track supplies, let me consume items, and include what remains in the next prompt.”
2. A separate authoring conversation opens. It can receive the selected Chat's cast and a chosen excerpt, but code logs and authoring instructions never become story Messages or Memories. A coding model is selected independently from the prose model.
3. The agent reads the installed SDK version, relevant Box documentation, and a small worked example. It checks whether changing an existing Box's setup or preset already satisfies the request before generating another Box. Existing `GET /api/boxes` metadata is useful for discovery but is not the entire SDK contract.
4. It creates an ordinary Box in a staging workspace, builds it, and gets compiler, loader, and user-flow diagnostics. The UI shows the actual rendered result and any prompt contribution in a disposable test story. For an inventory, verify consuming an item, the next Prompt Plan, selecting another Swipe, and reopening persisted state.
5. **Install** activates the checked artifact, with the current restart requirement visible. Installing makes it available app-wide; **Add to this Chat** uses the existing per-Chat lifecycle. Keep these two scopes distinct.
6. The writer asks for revisions in the same authoring session. Revised code goes through the same staging and verification path. Failed candidates leave the installed source untouched; storage changes are reported before activation.

The authoring service is host infrastructure. Generated story features are Boxes. Making an authoring Box install other Boxes would entangle chat enablement with application-wide code management and would not remove the need for a host runner.

The first tool surface can be small: read SDK/docs/examples, inspect installed Boxes, edit the candidate's files, run its checks/build, exercise its preview, and install the finished artifact. Derive contract information from existing SDK/schema sources; do not create a second handwritten capability catalog or a Cordis-style general reflection system just to start.

## Where the idea helps, and where it does not

An **inventory or resource mechanic** is the best first experiment: explicit Moves, deterministic outcomes, a small window, prompt contribution, and Variant records exercise the existing contract without relying on prose extraction. A **relationship tracker** can exercise digests and writer corrections, but needs explicit definitions of what the values mean and what evidence changes them. A **quest journal, clue board, or custom letters interface** is also plausible within Box windows, reads, lenses, and records. These are proposed applications, not shipped features.

Whole-app themes, arbitrary UI replacement, and general video editors are weaker initial targets. DSH's theme demo asks to restyle the entire application; DitzyTavern deliberately confines Box stylesheet selectors to the Box's classes. Boxes also compose through the Prompt Plan, not through a dependency scheduler or access to each other's current outputs. Preserve those boundaries unless a real requested feature proves them insufficient. ([styling implementation](../../scripts/build-box-client.ts), [Box rules](../box-system/README.md#the-rules), [design direction](../../DESIGN.md))

The creative opportunity is to let a writer invent the rules and instruments of their story. A generic application builder would dilute that advantage and expand the support burden.

## Smallest useful experiment and decision

Before building an embedded agent UI, use an existing coding agent against the documented Box contract to create one inventory Box, revise it twice through natural-language feedback, and install it through the current build/restart path in a disposable environment. Record where human code edits, host changes, or clarification were required. Verify the actual user flow and Prompt Plan; a successful compile is not enough.

Proceed to an in-app authoring session if that experiment produces a useful, revisable Box without changes scattered through the host. If it needs host edits, first determine whether an SDK export is missing or whether the requested mechanic does not fit the Box model. Do not turn the failure into an unrestricted “edit the app” escape hatch.

The first release would introduce an authoring session, runner workspace, and staged install action. It would replace the user's manual folder creation/build/copy workflow while retaining one Box format and runtime. No Cordis dependency, second plugin SDK, marketplace, generalized hot-reload system, or story tool-calling migration is required to establish whether the feature is worth shipping.

**Verdict:** strong product fit for conversational Box creation; weak justification for copying DSH's whole extensible agent runtime. The feature has a credible foundation, but the builder, activation lifecycle, and execution boundary make it more than a mode toggle. Generation quality, iteration cost, and the amount of human repair remain unmeasured until the experiment is run.
